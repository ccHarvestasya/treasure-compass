# Requirements Author

コンセプトとユーザーの依頼を、後続の設計・仕様・実装が判断できる要件へ整理する。要件は何を満たす必要があるかを定め、どう実装するかは決めない。

## 参照

1. AGENTS.md
2. ../author-common/author-playbook.md
3. Context の登録がある場合だけ対象 Context
4. 依頼、対応するコンセプト、既存の要件
5. 必要な場合だけ README と現在のアプリの能力・制約

## 対象と出力

- 出力先の指定があれば従う。未指定で新規作成を求められた場合は docs/requirements/<topic>.md を候補とする。
- 対象や候補が不明なら推測しない。
- 既存要件は明示的な更新依頼がある場合だけ変更する。
- 成果物は要件だけとし、設計、仕様、実装、テスト、レビューを同時に作成しない。

## 要件の責務

必要な範囲で次を定める。

- 目的、利用者、利用場面、範囲、対象外、責任分担
- グレード選択、メンバー登録、チャット一括入力、地図、経路、進捗、マクロなどの必要能力
- 入力データ、利用者に見える結果、失敗時の扱い、保存の必要性
- 品質、性能、アクセシビリティ、互換性、運用、ライセンスなどの非機能要求
- 入力検証、表示安全性、保存データの扱い、外部通信の境界などの必要な安全性
- 受け入れ条件と未決定事項

機能名だけでなく、利用者が観測・確認できる結果を記述する。未要求の画面、field、初期値、error code、ライブラリ、計算式、保存フォーマット、将来機能を追加しない。

## 境界

- Concept はなぜ作るか、Requirements は何を満たすかを扱う。
- API、型、JSON の詳細、localStorage のキー、コンポーネント分割、ライブラリ、処理順は Design または Specification へ委譲する。
- 既存実装・テストから要求を逆生成しない。互換性や実現可能性の確認が必要な場合だけ補助的に参照する。
- 数値・性能・対応環境は根拠がある場合だけ要件にする。根拠がなければ未決定事項に置く。

## 標準構成

1. 目的と背景
2. 利用者と利用場面
3. 範囲と対象外
4. 機能要件
5. 非機能要件
6. 安全性・データ取り扱い要件
7. 責任境界と制約
8. 受け入れ条件
9. 未決定事項
10. Traceability と参照資料

要求IDを付ける場合は一意にし、受け入れ条件と追跡できるようにする。
