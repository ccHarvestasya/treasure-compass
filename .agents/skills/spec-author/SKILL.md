# Specification Author

要件と基本設計を、利用者・実装者・テストが同じ結果を判定できる外部契約へ具体化する。何が観測でき、どの入力をどう扱い、どの条件で成功・失敗するかを定める。内部コード構造は必要以上に固定しない。

## 参照

1. AGENTS.md
2. ../author-common/author-playbook.md
3. Context の登録がある場合だけ対象 Context
4. 対象仕様、承認済み要件、設計、関連仕様
5. 必要な場合だけ README、公開 UI、型、定数、静的 JSON、テストを既存契約との照合に使う

## 仕様の責務

対象に必要な範囲で次を一意にする。

- 適用範囲、対象外、用語、責任境界
- UI 操作、入力形式、出力、空状態、ローディング、エラー
- チャット解析、マップ名・座標検索、経路計算、テレポート点、マクロ生成の外部挙動
- JSON の必須構造、画像ファイル対応、グレード設定、保存対象
- localStorage の復元、削除、破損時の扱い、互換性
- validation、正規化、順序、丸め、決定性、サイズ・性能制約
- ユーザー入力、HTML 表示、外部通信、データ漏えいを含む安全な失敗
- 受け入れ条件、fixture、ブラウザ確認、未決定事項

根拠のない初期値、field、閾値、エラー、互換動作を推測しない。

## 仕様にしない内容

上流にない機能、設定、field、fallback、将来拡張、内部 class / function / module、CSS、library、framework、テスト実装方式を追加しない。既存コードの挙動だけを正式契約に昇格させない。方式が複数で上流判断がない場合は未決定事項にする。

## 標準構成

1. 概要と適用範囲
2. 対象外、用語、責任境界
3. 前提と設計原則
4. UI と操作契約
5. 入力・出力・データ形式
6. 状態、保存、ライフサイクル
7. validation、error、禁止事項
8. 計算・決定性・表示規則
9. 安全性、互換性、運用
10. 受け入れ条件と適合試験
11. 未決定事項と下流引継ぎ
12. Traceability と参照資料

各契約が実装者の推測なしに判定できるか、要求と設計へ戻って自己確認する。
