# Concept Author

要件定義の前に、Treasure Compass が解決する課題、誰にどんな価値を届けるか、どこまでを扱うかを整理する。成果物は「なぜ作るか」「誰のためか」「どの責任を持つか」であり、機能仕様や実装計画ではない。

## 参照

1. AGENTS.md
2. ../author-common/author-playbook.md
3. AGENTS.md に対象フェーズの Context が登録されている場合だけ、その Context
4. ユーザーの依頼、既存 README、既存のコンセプト
5. 必要な場合だけ、現在の画面や利用場面を確認する

## 対象と出力

- 出力先の指定があれば従う。未指定で新規作成を求められた場合は docs/concept/<topic>.md を候補とする。
- 既存ファイルは明示的な更新依頼がある場合だけ変更する。
- 成果物はコンセプトだけとし、要件、設計、仕様、コード、テスト、レビューを同時に作成しない。
- 対象ユーザーや課題が不明な場合は、既存資料から推測で確定せず、仮定または未決定事項に置く。

## 扱う内容

- 背景、課題、原因、放置した場合の影響
- 対象ユーザー、関係者、主要な利用場面
- マップ情報の整理、巡回順の把握、チャット入力の負担軽減など、確認できた提供価値
- v1 の能力・責任領域、対象外、外部へ委ねる責任
- 判断原則、成功条件、前提、リスク、将来構想、未決定事項
- 要件定義へ引き継ぐ問い

利用場面は価値が説明できる粒度にとどめ、操作手順、画面項目、データ構造、処理手順へ展開しない。

## 決めない内容

明示された根拠がない限り、API、画面の詳細、field、schema、validation、error code、保存形式、依存、アルゴリズム、外部連携、詳細な安全対策、テストケースを新しく決めない。「便利そう」「一般的」「将来必要そう」だけの機能も追加しない。

## 標準構成

1. 概要
2. 解決したい課題
3. 目的
4. 対象ユーザーと主要利用場面
5. 提供価値
6. v1 のスコープと責任境界
7. 判断原則
8. 成功条件
9. 前提条件と主なリスク
10. 将来構想
11. 未決定事項
12. 要件定義への引継ぎ
13. 参照資料

事実、仮定、未決定事項、将来構想を分離し、根拠へ追跡できない記述を確認済み事実として書かない。

## 自己確認

- 背景、課題、目的、価値、スコープの因果が通っている。
- 対象ユーザー、利用場面、責任境界、対象外が明確である。
- v1 と将来構想、外部責任、未決定事項を混同していない。
- API、仕様、設計、実装、テストを先取りしていない。
- 追加内容を依頼または確認済み資料へ追跡できる。
- 既存ファイルの変更範囲が依頼どおりである。

独立レビューが必要なら concept-review を使う。この Skill 自身はレビュー成果物を作らない。
