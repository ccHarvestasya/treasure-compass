# Author / Review Orchestrator

文書、仕様、設計、実装などの作成と独立レビューを、管理者、作成者、レビュアーに分離して進行する。管理者は対象、権限、状態、Gate、コミット境界を管理し、成果物の作成とレビューはそれぞれ別エージェントへ委譲する。

この Skill は、利用可能なエージェント委譲機構があり、ユーザーが作成・レビューの分担または一連の半自動実行を求めた場合に使う。委譲機構がなければ、黙って単一エージェント運用へ変更せず制約を報告する。

## 役割

| 役割 | 責任 |
| --- | --- |
| Manager | 依頼分類、対象・権限・完了条件の確定、Skill選択、委譲、状態管理、Gate、コミット、最終報告 |
| Author | 選択された作成Skillに従う成果物の作成・修正と、必要な検証 |
| Reviewer | 対になるレビューSkillに従う独立レビュー、Finding、Gate、再確認、レビュー資料の作成 |

Author と Reviewer は別エージェントにする。モデルはユーザーまたは実行環境の明示的な指定を優先し、指定がなければ利用可能な適切なモデルを使う。指定モデルを利用できない場合は、無断で代替せず報告する。

Manager は対象整理、委譲、権限を伴う操作、結果統合に集中する。Author の成果物や Reviewer の独立判断を先回りして代行しない。

## Skill の選択

- ユーザー指定の作成SkillとレビューSkillがあれば、その組を使う。
- 指定がなければ、対象フェーズまたは成果物に対応する `*-author` と `*-review` の組を利用可能なSkillから選ぶ。
- 対になるSkillが見つからない、候補が複数あり結果が変わる、または対象が特定できない場合は推測で進めない。
- 複数フェーズの依頼は上流から順に分ける。異なる抽象度の成果物を一人の Author に混在させない。
- レビュー専用フェーズでは Author を起動せず、Reviewer に対象の修正を許可しない。

対象Skill、そのSkillが要求する資料、ユーザーが指定した資料だけを必要な範囲で確認する。プロジェクト固有の指針、検証規則、成果物形式、コミット規則があれば優先する。

## 実行モード

- **CREATE**: Author が成果物を作成または修正する。
- **REVIEW**: Reviewer が既存成果物を独立レビューする。
- **CREATE_AND_REVIEW**: Author の完了後、Reviewer が独立レビューし、必要なら修正と再レビューを行う。
- **CREATE_COMMIT_REVIEW**: 明示的なコミット許可がある場合に、対象変更を独立レビューした後、作成物と対応するレビュー資料を同じコミットにする。レビュー前に対象変更だけをコミットしない。

「作成してレビュー」「実装して確認」などは `CREATE_AND_REVIEW` とする。コミットは「コミットしてレビュー」「レビュー資料もコミット」など、ユーザーが明示した場合だけ `CREATE_COMMIT_REVIEW` へ追加する。push、tag、publish、リリース、外部メッセージ送信は別の明示的な許可が必要であり、コミット許可から推定しない。

## Manager brief

各 worker へ、必要なものだけを含む brief を渡す。

- task ID、目的、完了条件、実行モード
- worker の役割と使用するSkill
- 対象成果物、許可された変更パス、対象外パス
- 正式な根拠と確認時点、対象版または対象コミット
- 必要な検証、成果物形式、レビュー資料の出力先
- 作業開始時から存在する無関係な変更
- コミットを許可するか、Manager だけが行うか
- 修正サイクルでは、現在のサイクル番号、前回レビュー資料のパスと対象版、引き継ぐ Finding ID・状態、今回の修正対象

秘密情報、credential、個人情報、不要な入力データを brief や成果物へコピーしない。

## レビュー資料の不変性とサイクル番号

レビュー資料は、レビュー時点の判定を残す履歴資料であり、後続レビューのための状態ファイルではない。初回レビュー、修正後の再レビュー、再修正後の再レビューは、それぞれ別の資料として保存する。

- Manager はレビュー開始ごとに、対象成果物とレビュー系列に対して単調増加するサイクル番号を割り当てる。標準の命名は `*-review-001.md`、`*-review-002.md` のようにする。
- Reviewer への brief には、今回のサイクル番号と新規の出力パスを明記する。出力パスが既に存在する場合は使用せず、次の番号を割り当てる。
- Reviewer は過去のレビュー資料を参照して Finding の状態を追跡できるが、過去のレビュー資料を編集、上書き、削除、改名してはならない。過去資料の `Open` を後から `Resolved` に書き換えず、次の資料で同じ Finding ID の `Resolved`、`Reopened`、`Deferred` などを記録する。
- 各レビュー資料には、レビューサイクル番号、対象成果物と対象版、確認時点、Gate、Finding の状態、検証結果、未確認範囲を記録する。再レビュー資料には、前回資料への参照と今回確認した差分・解消条件を記録する。
- Manager は作業開始時に既存レビュー資料のパスとハッシュまたは差分状態を記録し、誤って変更されていないことを確認する。開始時から存在するユーザー変更なら無断で破棄・採用・ステージせず、分離できない場合はユーザーへ確認する。作業中に発生した変更ならその資料を採用せず、既存資料を復元せずに次のサイクル資料として作り直すよう Reviewer へ戻す。発生源を判定できない場合は `BLOCKED` とする。
- レビュー資料の出力先がユーザーまたは既存形式で指定されていない場合も、Manager がこのサイクル番号規則で一意な出力先を決める。単一の固定ファイルを複数サイクルで使い回さない。

## 作成

1. Manager は作業ツリー、現在のブランチ、対象、既存差分を確認し、今回の変更と無関係な変更を分離する。
2. Author を起動し、作成Skill、根拠、許可パス、完了条件を渡す。
3. Author は指定範囲だけを変更し、根拠のない要求や外部可視動作を追加しない。
4. Author は変更ファイル、根拠、検証結果、未確認範囲を返す。レビューを自己承認しない。
5. Manager は差分と検証結果を確認する。対象外変更は採用せず、既存のユーザー変更を取り消さない。

## 作成物とレビュー資料のセットコミット

`CREATE_COMMIT_REVIEW` では、レビュー前に対象変更だけをコミットせず、最終レビューが完了した後に作成物と対応するレビュー資料を同じコミットへまとめる。

1. Author の変更、Reviewer が今回作成したレビュー資料、ステージ済み変更、未追跡ファイルを確認する。
2. Reviewer の最終 Gate が確定しており、`BLOCKED` または必須修正未解決でないことを確認する。必須修正がある場合はステージせず、次のレビューサイクルへ戻す。
3. レビュー開始時に記録した対象成果物のパス・ハッシュまたは差分状態と、レビュー後の状態を比較する。対象成果物がレビュー中に変わっていればセットコミットせず、新しい対象版として再レビューする。
4. コミット開始前の `git diff --cached --name-only` を記録し、既存のステージ済み変更を保護する。対象成果物と今回のレビュー資料のパスだけを明示してステージし、無関係な既存変更を分離できない場合は `BLOCKED` とする。既にコミット済みの過去レビュー資料は再ステージしない。
5. プロジェクト固有の検証、ステージ済み差分、whitespace error、コミットメッセージ規則を確認してコミットする。
6. コミット本文とコミットIDを確認し、その同一コミットに作成物と対応レビュー資料の両方が含まれることを確認する。

レビュー資料が対象成果物と別コミットにならないようにする。修正サイクルでは、修正した対象成果物と新しいレビュー資料を次のセットコミットへ含める。レビュー前に対象変更を固定する必要がある場合は、コミットではなく対象版、作業ツリー差分、または一時的な参照で追跡する。

## 独立レビュー

別の Reviewer を起動し、対象レビューSkill、対象成果物、正式な根拠、依頼範囲を渡す。`CREATE_COMMIT_REVIEW` ではレビュー対象の版、作業ツリー差分、確認時点を指定する。Manager は対象成果物のパス・ハッシュまたは差分のフィンガープリントを記録して Reviewer に渡し、レビュー中は対象成果物を読み取り専用として扱う。レビュー前に対象コミットを作成してはならないため、コミットIDはセットコミット完了後に確定する。

Author の推測、自己評価、意図した判定、疑っている欠陥を Reviewer へ誘導材料として渡さない。Reviewer は対象成果物と過去のレビュー資料を変更せず、指定された今回の新規レビュー資料だけを作成する。対象箇所、根拠、影響、必要な修正、再確認条件、検証結果、未確認範囲、Gate、レビューサイクル番号を示す。

レビュー資料が必要な場合、Reviewer は指定された今回の出力先へレビュー成果物を新規作成できる。既存のレビュー資料を更新してはならない。レビュー資料はレビュー対象の変更パスから分離する。

## Gate と修正ループ

対象レビューSkillのGateを優先し、Manager は概ね次のように扱う。

- **READY**: 必須修正なし。レビュー完了。
- **READY WITH CONDITIONS**: 対象Skillが許容する場合、条件を明示してレビュー完了。
- **REVISION_NEEDED**: 対象レビューSkillが必須修正を要求するGate。`REVISE`、`REVISE CONCEPT` など名称が異なっても、この制御状態へ正規化し、最小限の修正だけを Author へ返す。
- **BLOCKED**: 対象不明、上位判断不足、権限不足、委譲機構・指定モデル不足などで安全に継続できない。
- **OUT_OF_SCOPE**: 依頼範囲外。現在の成果物を変更せず、別作業として報告する。

任意改善だけで差し戻さない。重大度とGateの関係は対象レビューSkillを優先する。

`REVISION_NEEDED` の場合は、Manager が Author brief に前回レビュー資料のパス、対象版、Finding ID・状態、必要な修正範囲を明記し、同じ Author が指摘に必要な範囲だけを修正する。同じ Reviewer は次のサイクル番号の新規レビュー資料で再確認する。前回のレビュー資料は不変のまま残し、再レビュー資料で前回 Finding の状態と今回の確認結果を記録する。`CREATE_COMMIT_REVIEW` では修正した対象成果物と新しいレビュー資料を、最終レビュー後に同じセットコミットへ記録する。履歴を書き換える操作は、ユーザーが明示しない限り行わない。

再レビューは既定で最大3回とする。ユーザー指定があれば優先する。上限までに完了Gateへ到達しなければ、未解決事項と必要な判断を示して `BLOCKED` とする。

## セットコミット後の確認

`CREATE_COMMIT_REVIEW` でレビューが完了したら、作成物と対応レビュー資料を別々にコミットせず、セットコミットとして完了させる。

1. Reviewer が最終サイクルのGate、Finding の状態、レビュー対象版、検証結果、未確認範囲を新しいレビュー資料へ記録する。初回を含む過去のレビュー資料は変更しない。
2. Manager は、各サイクルのレビュー資料が対象成果物を変更していないこと、互いに別パスであること、今回の作成物と追跡可能であることを確認する。
3. 対象成果物と今回のレビュー系列に属する未コミット資料を同じコミットへ明示的にステージする。過去のレビュー資料が既にコミット済みの場合は、新しいサイクルの資料だけを含める。ステージ済み差分と whitespace error を確認する。
4. プロジェクトの規則に従って、作成物とレビュー資料を含む一つのコミットを作成する。
5. コミット本文とコミットIDを確認する。最終報告では、全サイクルのレビュー資料、各資料が記録するGate・Finding状態、作成物とレビュー資料を含むセットコミットIDを示す。

レビュー資料が存在しない、サイクル番号が重複している、既存資料が変更されている、レビュー対象のフィンガープリントが変わっている、最終Gateが確定していない、作成物とレビュー資料の対応を追跡できない、無関係なステージ済み変更を分離できない、またはレビューが `BLOCKED` の場合はセットコミットを作成しない。途中レビューを記録するようユーザーが明示した場合も、既存資料を更新せず、そのサイクルの新規資料と対象変更を後続のセットコミットへまとめる。

## 検証

- 変更種別に応じたプロジェクト固有の検証を適用する。
- レビュー対象の作業ツリー版またはセットコミット、レビュー資料の対象範囲を分けて確認する。
- 未実行の検証や未確認の環境を成功扱いにしない。
- 検証が対象外なら `NOT APPLICABLE` または `SKIPPED`、実行不能なら `Not validated` として記録する。

## 状態

通常フロー:

`PLANNED → AUTHORING → VALIDATING → REVIEWING → READY`

コミットを伴うフロー:

`PLANNED → AUTHORING → VALIDATING → REVIEWING → REVIEW_COMPLETE → SUBJECT_AND_REVIEW_COMMITTED → READY`

修正時:

`REVIEWING → REVISION_NEEDED → AUTHORING → VALIDATING → REVIEWING`

停止時は `BLOCKED` または `OUT_OF_SCOPE` とする。

## 最終報告

次を区別して報告する。

- task、実行モード、各workerの役割と使用Skill
- 変更された対象成果物と、作成物・レビュー資料を含むセットコミットID
- レビュー系列の全資料（サイクル番号、パス、対象版）と対応するセットコミットID
- Reviewer のGate、Finding、対応状況
- 検証結果と未確認範囲
- 残存する仮定、条件、未決定事項
- 実行していない push、tag、publish などの操作

この Skill は委譲、状態、Gate、コミット境界を管理するものであり、個別の作成SkillとレビューSkillの代替ではない。
