# Author Playbook

作成系 Skill に共通する作業規律。製品、機能、サービス、ツール、ライブラリ、CLI、Web / Mobile アプリケーション、バックエンド、OSS、プロトコル、技術仕様、その他のソフトウェア・非ソフトウェアプロジェクトに適用する。工程固有の責務、標準構成、境界は各 Skill に委譲する。

## 根拠と情報の扱い

根拠は原則として次の優先順位で扱う。

1. ユーザーが明示した最新の判断・依頼
2. 承認済みの上流成果物
3. 対象工程の正式成果物
4. プロジェクト内の正式な契約・規約・制約
5. 補助資料
6. 既存実装・テスト・データ
7. 外部資料

対象 Skill または対象プロジェクトに明示的な Source of Truth / 優先順位規則がある場合は、それを優先する。ただし、古い資料でユーザーの最新判断を上書きしない。正式資料同士が矛盾し、優先順位を判断できず成果物の成立に影響する場合だけ確認する。

参照資料から得た内容は、確定事項、ユーザーの方針・要求、制約、仮案、未決定事項、対象外、将来構想、既存実装上の事実に分類する。仮案を確定事項にせず、既存実装を要求にせず、将来構想を現在スコープに入れず、未決定事項を推測で埋めない。

## 上流・下流の方向性

```text
Concept
  ↓
Requirements
  ↓
Specification
  ↓
Design
  ↓
Implementation / Test
```

下流成果物から新しい上流要求、目的、スコープを逆生成しない。実装されているから Requirement とみなす、テストに存在するから Specification とみなす、Design にあるから Concept の目的へ追加する、といった逆流を禁止する。既存実装・テスト・データは、現在の能力、互換性、実現可能性、既存契約との矛盾、移行影響の確認に限り補助的に参照する。

## Phase Context

Phase Context は正式資料の探索を助ける非規範的な補助情報であり、対象プロジェクトで明示的に登録・提供されている場合だけ使用する。Source of Truth ではなく、正式資料やユーザー判断と競合した場合は正式な根拠を優先する。Context だけから新しい要求・制約を確定せず、鮮度や根拠が不明なら正式資料へ戻って確認する。使用しないプロジェクトでは探索対象に含めない。

## 参照・成果物・変更範囲

依頼された成果物の作成に必要な範囲だけ参照する。存在するからという理由で無制限に探索しない。参照候補は、AGENTS.md 等のプロジェクト固有指示、対象 Skill、上流成果物、同一工程の既存成果物、README、正式仕様、既存契約、実装、テスト、データ、外部公式資料とし、対象 Skill の参照順序があれば従う。

- 指定された出力先、文書種別、既存プロジェクトの命名・配置規則に従う。
- 明示的な更新依頼がない既存成果物や対象外ファイルを変更しない。
- 関連変更が不可欠な場合だけ、必要性を確認して最小限に変更する。
- 下流文書、レビュー成果物、将来ロードマップをついでに作成せず、文書作業だけでコードを変更しない。
- 文書をきれいにするためだけの大規模リファクタをせず、ユーザー指定の範囲を超えない。

入力資料や上流要求にない機能、利用者、画面、設定、保存項目、数値、制約、エラー、品質要求、外部連携、将来機能、運用・セキュリティ要件を推測で追加しない。根拠不足の事項は、対象 Skill に従って未決定事項、質問、上流への差し戻し、下流への引継ぎとして扱う。

## 作成手順

1. 依頼内容、対象成果物、出力先、変更可能範囲を確認する。
2. 対象 Skill とプロジェクト固有指示を確認する。
3. 必要な上流資料・正式資料・既存成果物を必要最小限参照する。
4. 情報を確定事項、要求、制約、仮案、未決定事項、対象外などに分類する。
5. 対象工程の抽象度に合う内容だけを採用する。
6. 根拠へ追跡可能な成果物を作成・更新する。
7. 対象 Skill の自己確認・validation を行う。
8. 変更範囲と成果物を確認する。

詳細な工程固有手順、標準構成、責務、境界は各 Skill に委譲する。

## Validation

validation は変更内容に比例させる。文書だけの変更で無関係な実装全体の lint / test / build を実行せず、必要に応じて Markdown、リンク、形式、リポジトリ固有の validation を行う。コード変更がある場合だけ対象コードに必要な lint / test / build を行う。未実行の検証を PASS と報告せず、実行不能なら理由を明示する。AGENTS.md 等に change-aware validation があればそれを優先する。

## 優先順位と外部操作

工程固有 Skill と共通 Playbook が競合した場合は、ユーザーの明示的指示、プロジェクト固有の上位指示、対象工程の Skill、共通 Author Playbook の順で扱う。既存の正式な優先順位規則があれば尊重し、共通 Playbook は工程固有 Skill より上位の規範にならない。

ユーザーまたは上位指示がない限り、commit、push、tag、release、publish、deployment、package publication、PR 作成を実行しない。

工程固有の詳細をコピーせず、具体例を大量に追加せず、同じルールを反復せず、共通原則だけを残す。
