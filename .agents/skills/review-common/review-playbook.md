# Review Playbook

レビュー系 Skill 共通の規則。レビューは対象を修正せず、根拠に基づいて適合性、欠落、矛盾、リスク、未確認範囲を記録する。

## 参照

1. AGENTS.md
2. この playbook
3. 対象 Skill と明示された補助資料
4. ユーザー指定の対象、README、上流文書、同一フェーズの成果物
5. 必要な範囲のコード、テスト、静的データ、設定、公式資料

対象の抽象度を越えて、実装・仕様・要件を自由に再設計しない。対象外の詳細不足は、引継ぎまたは未確認範囲とする。

## 手順

### Phase 0: 対象と差分

- 対象ファイル、対象機能、確認時点、依頼範囲を確定する。
- 候補が複数または不明なら推測で選ばない。
- git status と差分を確認し、ユーザー変更を誤って対象化しない。

### Phase 1: 根拠

- 主張ごとに依頼、上流文書、README、実装、テスト、データの根拠を確認する。
- テストや実装の現在値だけで利用者向け仕様を正当化しない。
- 依頼にない機能、保存方式、互換性、UI、依存を指摘から発明しない。

### Phase 2: 対象に応じた確認

- 利用者、責務、対象外、画面・データの境界
- 入力、出力、状態、保存、エラー、空状態、ローディング
- 型、静的 JSON、画像、ファイル名、参照先の整合
- チャット解析、座標変換、経路計算、マクロ出力
- localStorage、ユーザー入力、JSON、HTML 表示、外部通信の安全な扱い
- 既存テストの境界・失敗系・決定性・回帰保護
- README、package metadata、実行コマンド、公開成果物の整合

### Phase 3: 指摘の採用

正式な指摘は、対象資料へ追跡でき、具体的な影響と最小修正または確認条件を説明できるものに限る。一般論、好み、未依頼の将来改善は任意改善または対象外へ分ける。

同じ根本原因を重複して数えない。上流資料の不足は、現在の対象で安全に判定できるなら Upstream Feedback のみ、判定不能なら現在フェーズの指摘と上流への引継ぎを分ける。

## 判定と成果物

各レビュー Skill は READY / REVISE など対象に合う判定値を定める。重大度や Gate を checklist だけで自動決定しない。指摘がない場合も確認範囲と未確認範囲を記録する。

レビュー中はコード、仕様、要件、README、テスト、fixture、設定を変更しない。未実行の検証、未確認のブラウザ環境、未確認の外部サービスを成功扱いにしない。個人情報、チャット本文、保存データ、環境変数を成果物へ含めない。ユーザーの明示なしに commit、push、tag、publish を行わない。
