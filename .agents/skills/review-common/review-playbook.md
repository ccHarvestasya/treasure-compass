# Review Playbook

レビュー系 Skill に共通する作業規律。製品、サービス、Web / Mobile アプリケーション、CLI、ライブラリ、SDK、バックエンド、プロトコル、OSS、技術仕様、インフラ、その他のプロジェクトに適用する。工程固有のレビュー基準、重大度、Gate、Finding ID、Checklist は各 Review Skill に委譲する。

## 対象と責務

レビュー対象、対象工程、確認時点、レビュー範囲、未確認範囲を最初に確定する。候補が複数または不明なら推測で選ばない。Review は対象工程の成果物がその工程の責務を満たすかを確認するものであり、製品・仕様・設計・実装をより高機能にする作業ではない。レビュー対象を直接修正せず、レビュー成果物だけを作成・更新する。

## 根拠と情報の優先順位

根拠は原則として次の優先順位で扱う。

1. ユーザーが明示した最新の判断・依頼
2. 承認済みの上流成果物
3. レビュー対象工程の正式成果物
4. プロジェクト内の正式な契約・規約・制約
5. 同一工程の関連成果物
6. 補助資料
7. 下流成果物・既存実装・テスト・データ
8. 外部資料

対象 Skill またはプロジェクト固有指示に Source of Truth / 優先順位規則がある場合は、それを優先する。ただし、古い資料でユーザーの最新判断を上書きしない。正式資料同士の優先順位が決められずレビュー判定に影響する場合は、未確認または上流問題として扱う。

主張ごとに依頼、上流成果物、対象成果物、正式契約などの根拠を確認し、根拠のない問題を作らない。

## 工程と問題の分類

問題を発見しても、直ちに正式 Finding にしない。まず次の工程へ分類する。

```text
Upstream
  → レビュー対象より前の工程で決めるべき問題

Current Phase
  → 現在レビューしている成果物自身の問題

Downstream
  → 後続工程で決めればよい問題

Out of Scope
  → 現在のレビュー対象外
```

```text
Upstream problem
  → Upstream Feedback

Current Phase problem
  → 正式 Finding 候補

Downstream problem
  → Deferred / 保留 / 下流への引継ぎ

Out of Scope
  → 原則として正式 Finding / Deferred に記録しない
```

各 Review Skill が具体的な工程分類を定義する場合は、それを優先する。上流問題のために現在成果物が成立しない場合は、上流問題と現在工程への影響を分けて記録し、個別 Skill の Gate 規則に従う。

## 下流から上流への逆生成禁止

下流の Specification、Design、Implementation、Test 等に存在する内容だけを理由に、現在または上流工程へ新しい要求、目的、スコープ、責任を追加しない。

```text
実装されている
  → Requirement である

テストされている
  → Specification である

Design に存在する
  → Concept に必要である
```

この逆推論を禁止する。下流成果物は、現在の状態、整合性、互換性、回帰、実現可能性、上流成果物との明白な矛盾を確認する場合だけ補助的に参照する。正式な不足は、レビュー対象または適用される上流根拠から説明できなければならない。

## Finding の採用

正式 Finding は、次のすべてを満たす場合だけ採用する。

1. レビュー対象または適用される正式な根拠へ追跡できる。
2. 現在レビューしている工程で解決すべき問題である。
3. 具体的な矛盾、欠落、曖昧さ、責任上の問題、適合性違反等を説明できる。
4. 放置した場合の具体的な影響を説明できる。
5. 何を修正または確認すれば解消したと判断できるか示せる。

一般的なベストプラクティス、好み、より高い機能・安全性・拡張性、将来の必要性、他製品の慣行、Checklist の項目、実装やテストへの存在だけを理由に Finding を作らない。個別 Review Skill が追加条件を定める場合は、それを適用する。

正式化する前に、現在工程の問題か、上流・下流・対象外ではないか、一般論や将来拡張ではないか、下流から逆生成していないか、重複していないか、影響と解消条件を対象工程の抽象度で説明できるかを自己反証する。反証できない候補は Finding にしない。Finding 数をレビュー品質とみなさない。

## 重複・上流・下流の整理

同じ根本原因から生じる症状は原則として1つの Finding に統合する。修正責任、重大度、対象工程が異なる場合だけ分離する。複数 Reviewer が同じ問題を発見した場合も Chair またはメイン Reviewer が統合する。

上流成果物の不足・矛盾・曖昧さは、現在工程の欠陥に見せかけず `Upstream Feedback` として記録する。後続工程で決めれば対象成果物を変更せず解決できる事項は `Deferred`、保留、下流への引継ぎとして整理する。対象外は原則として Deferred に変換せず、対象外であること自体を改善候補として蓄積しない。レビュー境界の説明に必要な場合だけ、Review Scope に簡潔に記録する。

## 抽象度、参照、差分

レビューは対象成果物と同じ抽象度で行う。対象より下流の詳細がないことを不足扱いせず、対象より上流の判断を勝手に変更しない。

参照は判定に必要な範囲に限る。候補は AGENTS.md 等のプロジェクト固有指示、対象 Review Skill、review-common、ユーザー依頼、上流正式成果物、レビュー対象、同一工程の関連資料、正式契約・制約、下流成果物、実装・テスト・データ、外部公式資料とする。存在するからという理由だけですべて読まない。対象 Skill が参照順序を指定する場合は従う。

差分レビューでは依頼された範囲に従い、周辺文脈を確認しても差分外の既存問題を無制限に Finding 化しない。全体再レビューが指定された場合は対象成果物全体を評価し、Review Scope を成果物に明記する。

## Review と Author の分離

レビュー中は上流成果物、レビュー対象、下流成果物、README、コード、テスト、fixture、設定、ビルド構成を変更しない。Finding の `Required Change` / `最小修正` には、何が満たされれば解消するかを対象工程の抽象度で示すが、修正後の完成文書や下流設計を作成しない。Author による修正ワークフローが別途ある場合も、Reviewer 自身の責務とは分離する。

## 過去 Finding、重大度、Gate

既存レビューがある場合は、対象 Skill の状態体系に従い、New、Open、Resolved、Reopened、Deferred、Superseded 等の履歴を尊重する。Resolved の問題を根拠なく新しい ID で再作成せず、再発時は可能なら Reopened とする。

重大度、Gate、判定値、Finding ID prefix は共通 Playbook で決めない。Checklist や Finding 件数だけで機械的に決定せず、対象 Skill の基準と実際の影響に従う。成果物の共通構成は `output-format.md` を参照する。

## Validation と外部操作

Validation はレビュー対象と変更内容に比例させる。文書レビューだけで無関係な実装全体の lint / test / build を自動実行せず、必要に応じて Markdown、リンク、構造、リポジトリ固有の検証を行う。コードレビューで実行検証が必要な場合は対象範囲に必要なテストだけを選択する。未実行の検証を PASS と報告せず、実行不能な検証や未確認の外部サービス・環境は理由とともに記録する。AGENTS.md 等に change-aware validation があれば優先する。

ユーザーまたは上位指示がない限り、commit、push、tag、release、publish、deployment、PR 作成、その他の外部システムへの変更を実行しない。レビュー成果物には思考過程、credential、secret、token、password、個人情報、機密データ、環境変数の値、入力の生データを不要に記録しない。
