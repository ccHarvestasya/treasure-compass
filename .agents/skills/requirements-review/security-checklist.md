# Requirements Safety / Security Checklist

この Checklist は、対象資料に追跡できる安全性、責任、境界、失敗時挙動を確認するための探索補助である。単独で新しい Requirement、責任、Threat Model、Scope、Design、重大度を生成しない。対象に適用できる項目だけを使い、該当しない項目は N/A とする。

## 入力と外部境界

- 外部入力、信頼境界、入力を扱う主体の責任が必要な範囲で明確か。
- 空、不正、過大、範囲外、未知、重複、解析不能な入力を扱う必要があるか。
- 入力を別の意味のデータ、コード、命令、参照として解釈する境界が明確か。
- 不正入力や境界違反時に、外部から観測できる安全な結果が必要か。

## データと情報資産

- 保護対象、情報資産、データの所有者・責任主体が明確か。
- 不要な公開、漏えい、改変、欠落、誤利用を防ぐ必要が根拠から導けるか。
- データの完全性、機密性、privacy、保持・削除を含むライフサイクルが必要な範囲で定義されているか。

## 認証・認可と責任

- authentication / authorization、役割、権限、代理操作の要求が必要な範囲で明確か。
- trust boundary と responsibility boundary を越える操作や情報共有の責任が明確か。

## 失敗・資源・回復

- 失敗時に安全な状態、誤った成功、状態の破棄、再試行の責任が必要な範囲で定義されているか。
- availability / resource safety、過大な入力や処理、回復可能性、復旧後の整合性が要求として必要か。

## 外部連携・相互運用性

- 外部主体、依存先、交換する情報、相互運用性、失敗時の責任境界が明確か。
- 外部連携、公開、監査、法的・規制上の制約が上流根拠から必要か。

## 適用と Finding

全項目を機械的に適用せず、対象範囲と根拠に応じて確認する。正式な Security Finding は、ユーザー判断、Concept、Requirements、正式な外部契約・法的制約、または明示された責任へ追跡でき、Requirements レベルの外部影響と再確認条件を説明できるものに限る。一般的なベストプラクティス、実装 hardening、Checklist の項目だけを理由に Requirement や Finding を作らない。
