# Concept Review

コンセプトシートについて、企画の核と境界が明確で、後工程が意図を誤解せずに要件定義へ進めるかを判定する。完成された製品仕様へ近づけるレビューではない。

レビュアー自身が企画者になって、新機能、一般化、将来機能、詳細仕様、アーキテクチャを要求または決定しない。レビュー対象は修正せず、根拠のある指摘と判定だけを作成する。

## 対象と根拠

- ユーザーが指定したコンセプトシートと版を対象にする。対象が特定できず候補が複数ある場合は推測で選ばない。
- 根拠は、ユーザーが明示した最新の意思決定、正式なコンセプトシート、コンセプトへ正式な制約を与える上位資料、既存レビューと解決履歴、補助資料の順に扱う。
- 要件、設計、実装などの下流資料から、詳細や新しい要求をコンセプトへ逆流させない。下流資料との矛盾では、コンセプトの不足だけでなく下流側の逸脱も検討する。
- 既存のレビュー形式、重大度、Gate、Finding ID 規則があればそれを優先する。なければ、この Skill の既定を使う。

## レビュー領域

見出し名ではなく、次の意味に対応する内容を評価する。7つの見出しが文字どおり存在することは要求しない。

1. **コンセプト概要**: 何を作るか、中心目的、主要概念と必要な関係を、実装知識なしで理解できるか。
2. **解決する課題 / 対象ユーザー**: 誰がどの状況で何に困り、その課題を改善する意味が分かるか。課題と対象ユーザーが対応しているか。
3. **提供価値 / 代表利用フロー**: 利用前後の変化、中心価値、代表的な正常系が課題と対応しているか。機能一覧や詳細操作に価値が埋没していないか。
4. **v1 スコープ / 対象外**: v1 の成立範囲、隣接機能との境界、意図的に扱わないものが分かるか。提供価値、対象外、将来構想と矛盾していないか。
5. **責任境界・判断原則**: プロジェクトが責任を持つものと持たないものが分かり、後工程の判断に使えるか。原則同士やスコープと矛盾せず、実装方式に置き換わっていないか。
6. **成功状態**: 対象ユーザーに何が可能になれば企画として成立するかが、提供価値と v1 に整合しているか。
7. **要件定義への引継ぎ**: 後工程で具体化する問いが適切に分離され、コンセプト事項の先送りや隠れた詳細仕様になっていないか。

対象ユーザー、目的、課題、価値、v1、対象外、責任境界、判断原則、成功状態の相互整合も確認する。特に次を照合する。

- 課題 ↔ 提供価値
- 提供価値 ↔ v1 スコープ
- v1 スコープ ↔ 対象外
- v1 スコープ ↔ 成功状態
- 責任境界 ↔ 提供価値
- 判断原則 ↔ v1 スコープ
- Concept ↔ Requirements Handoff

## 工程境界

問題や未決定事項を発見したら、Finding を作る前に所属工程を判定する。

- **Concept**: 作るもの、対象ユーザー、課題、価値、主要概念、v1、対象外、責任、判断原則、成功状態が理解できない、矛盾する、または未決定のままでは企画が成立しない。原則として正式 Finding の対象にする。
- **Requirements**: 操作、入力条件、状態遷移、権限、ライフサイクル、セッション、保存期間、同時操作、例外処理、非機能要件、対応環境、外部連携条件など、具体的な外部挙動である。コンセプトが成立するなら Concept Finding にせず、必要に応じて引継ぎ漏れを指摘する。
- **Design**: API、データモデル、データベース、プロトコル、キャッシュ、同期方式、アルゴリズム、ライブラリ、フレームワーク、デプロイ、内部モジュールなど、実現方式である。内容の正誤はレビューしない。過剰な設計記述がコンセプトを曖昧にする場合だけ、除去または後工程への移動を求める。
- **Out of Scope**: 現在の企画または v1 に不要である。将来必要になる可能性だけで Finding にしない。

詳細がないこと自体を欠陥としない。正確な画面操作、全フロー、例外、状態遷移、上限、timeout、保存期間、権限細則、error 処理、同期、性能値、API、データ構造、技術構成、実装方法は、それがコンセプト成立に不可欠でない限り要求しない。

## 境界逸脱の確認

次がコンセプトの境界を曖昧にしている場合は Finding 候補にできる。

- UI、API、データ、データベース、通信、内部構造、アルゴリズム、error 処理、非機能要件、実装、テスト、CI/CD の詳細が過剰に混入している。
- 将来必要かもしれない機能、想定外の利用者・用途、一般的な「あるべき機能」が v1 へ追加されている。
- 再利用性や実装都合だけで抽象概念を追加し、利用目的、ユーザー、ライフサイクル、責任、ワークフロー、用語、成功状態が異なる概念を統合している。
- 対象外が別の箇所で対象内へ戻り、責任範囲や自動化範囲が無制限に広がっている。

技術用語があるだけで Finding にしない。技術自体が目的、外すと企画の意味が変わる、または変更不能な制約なら、コンセプトに含められる。

セキュリティ、プライバシー、信頼性は、責任境界、信頼境界、禁止事項、中核価値、根本的制約に影響する場合だけ Concept Finding とする。一般的なベストプラクティス、暗号方式、可用性、拡張性を機械的に要求しない。

## Finding の採用

Finding を確定する前に、次を反証する。

- 修正すると「何を、なぜ、誰のために、どこまで作るか」が明確になるか。
- Requirements または Design で決めれば十分ではないか。
- レビュアー自身が欲しい機能、一般論、将来拡張を要求していないか。
- 対象外または Requirements Handoff へ正当に分離されていないか。
- 同じ根本原因を別の Finding として重複計上していないか。

反証できない Concept 問題だけを正式 Finding にする。Finding 数を増やすことを品質とみなさない。

各 Finding には次を含める。

1. 対象箇所と、何が不明・矛盾・過剰・不足しているか
2. Concept レベルの問題である理由
3. 目的、対象ユーザー、価値、v1、責任、成功状態への影響
4. Concept レベルで明確化または修正すべきこと

実装方法を Required Change として指定しない。

## 重大度

既存の体系がなければ、次を使う。

- **Critical**: 何を作るか決まっていない、排他的な目的が共存する、対象ユーザーと価値が根本的に矛盾するなど、コンセプト自体が成立しない。
- **Major**: 主要概念、v1 と対象外、重要な責任境界、価値と成功状態などが曖昧または矛盾し、要件定義で意図やスコープが大きくぶれる。
- **Minor**: 成立は妨げないが、誤読、軽微な境界不明瞭、用語不統一、冗長性を生む。文書を磨くためだけに大量作成しない。

## 過去 Finding

既存レビューがあれば、各 Finding を `Open` / `Resolved` / `Reopened` / `Deferred` / `Superseded` として追跡する。解消済みの問題を理由なく再作成せず、同じ問題の再発は可能なら新しい ID ではなく `Reopened` とする。

## Gate

既存の Gate がなければ、Finding 数だけでなく、コンセプトを Source of Truth として要件定義を始めても企画意図を大きく誤解しないかに基づいて判定する。

- **READY**: コンセプトとして必要な情報が明確である。方向性へ影響しない Minor が残っていてもよい。
- **READY WITH CONDITIONS**: コンセプトは成立しているが、後工程開始前または並行して解消すべき限定的な Major がある。条件を明示する。
- **REVISE CONCEPT**: Critical、または要件定義を大きく誤誘導する Major があり、企画意図やスコープが不安定である。
- **BLOCKED**: 必要な情報源や上位判断がなく、または正式決定が相互矛盾し、レビュー対象の修正だけでは判定できない。詳細要件の未決定だけを理由にしない。

## レビュー手順

1. 対象、版、範囲、正式な根拠、既存レビューを確定する。
2. 内部的に「誰が、何のために、何を使い、何が改善される企画か」を一文で説明する。説明できなければ概要、課題、価値を重点確認する。
3. 7つのレビュー領域と、その相互整合を確認する。
4. 文書内の問題や詳細を Concept / Requirements / Design / Out of Scope に分類する。
5. 境界逸脱、過剰設計、過剰共通化を確認する。
6. Finding 候補を反証し、採用条件を満たすものだけを残す。
7. 企画の成立性と要件定義への誤誘導リスクから Gate を決める。

## 出力

既存の正式フォーマットがなければ、少なくとも次を記録する。

### Review Summary

- レビュー対象と版
- 対象範囲と未確認範囲
- Gate
- Critical / Major / Minor の件数
- Reopened / Resolved の件数

### Concept Assessment

目的、対象ユーザーと課題、提供価値、v1、境界、成功状態、Requirements Handoff、工程境界の品質を簡潔に評価する。

### Findings

Critical、Major、Minor の順に記述する。既存の ID 規則がなければ `CR-XXX` を使う。各 Finding は次の形にする。

```markdown
## CR-XXX — [重要度] タイトル

**状態:** Open

**対象:** 該当箇所

**問題:** 何が不明、矛盾、過剰、または不足しているか。

**Concept上の影響:** 企画のどの部分が不安定になるか。

**Required Change:** Conceptレベルで明確化または修正すべきこと。
```

Finding がなければ `Open Concept Findings: None` と明示する。

### Gate Rationale

Finding 数だけでなく、企画の核と境界が成立し、後工程が誤解せず進めるかという観点で判定理由を説明する。

## 自己確認

- 見出しの有無ではなく、7領域の意味と相互整合を評価した。
- 詳細要件、設計、実装の不足を Concept Finding にしていない。
- 新機能、一般化、将来機能、一般的ベストプラクティスを要求していない。
- Finding 候補を工程分類し、反証してから採用した。
- 各 Finding に対象、Concept 上の理由、影響、必要な明確化がある。
- Gate は件数ではなく、企画の成立性と後工程への誤誘導リスクで決めた。
- 未決定の Requirements や Design が残ること自体を欠陥にしていない。

良いコンセプトレビューは文書を詳細化するのではなく、「何を、なぜ、誰のために、どこまで」を守り、要件定義へ安全に進める状態かを明らかにする。
