この文書は、Treasure CompassとMob Compassについて、「何を、誰のために、どこまで作るか」を定める。具体的な入力、画面、データ、経路計算、保存、チャット形式、運用は要件定義以降で決める。検討済みの詳細は、非規範的な一時別紙である[要件定義以降への検討メモ](./requirements-notes.md)に退避する。

## 1. コンセプト概要

Treasure CompassとMob Compassは、FFXIV内の巡回対象を登録し、マップ間の移動が最小になるよう算出された最短ルートと進行を管理するブラウザツールである。ここでいうマップ間の移動とは、あるマップから別のマップへの移動を指す。別のマップへはテレポで移動することが多く、ゲーム内通貨とロード時間がかかるため、その移動をなるべく抑える。トレジャーハント用のTreasure Compassと、モブハント用のMob Compassは別の公開単位とするが、この巡回支援の根本的な考え方を共有する。両プロダクトのURLは固定しない。

Treasure Compassでは対象をメンバー名で表し、同時点では一人のメンバーに一つの宝箱座標が対応する。一人が複数の地図を持っていても、地図は一つずつ開封され、座標は順次提示される。

Mob Compassでは対象をモブ名で表し、一つのモブに複数の座標が対応する。この1対1と1対多の違いを扱いながら、対象の登録、マップ間の移動が最小になる最短ルートの算出、完了までの進行管理という体験を共通させる。

Mob Compassはすべてのモブを同じモブハントとして扱う。モブのランクや利用人数によって登録後の扱いを分けず、個人で使うか共有周回で使うかはユーザーに委ねる。

## 2. 解決する課題 / 対象ユーザー

### 解決する課題

- 複数の宝箱やモブについて、位置情報を整理し、マップ間の移動をなるべく抑えた巡回順を把握する負担を減らす。
- 周回中に、未完了の対象と現在の進行を把握する負担を減らす。
- モブハントのリーダーが巡回ルートと進行を管理し、参加者へ案内する負担を減らす。
- 宝箱とモブで共通する地図、移動、巡回、進行の考え方を重複して整備する負担を減らす。
- 新しいエリアや対象が追加された際に、巡回に必要な基礎情報を継続して整備できるようにする。

### 対象ユーザー

- パーティーメンバーの宝箱を巡回するTreasure Compassの利用者。
- 登録したモブを個人で巡回するMob Compassの利用者。
- 複数人のモブハントで巡回ルートと進行を管理するリーダー。
- 地図、移動拠点、モブ、位置情報を整備する管理者。

モブハントの参加者はプロダクトの直接の利用者とはせず、リーダーからチャットで案内を受ける関係者とする。

## 3. 提供価値 / 代表利用フロー

利用者は宝箱またはモブを入力し、地図と移動情報をもとに、マップ間の移動が最小になるよう算出された最短ルートを確認する。その順に対象を巡り、完了した対象を消し込むことで、残りの巡回を把握できる。Treasure Compassではメンバーに対応する一つの宝箱座標を、Mob Compassではモブに対応する複数の座標を扱うが、「入力 → 最短ルートの把握 → 巡回 → 進行管理」という価値の流れは共通する。

Mob Compassを共有周回に使う場合も、同じ流れをリーダーが管理し、参加者にはチャットで知らせる。別の利用者がリーダーを担う場合は、そのお知らせを取り込むことで管理を続けられる。

## 4. v1スコープ / 対象外

### v1スコープ

- Treasure CompassとMob Compassを別の公開単位として提供する。
- Treasure Compassで、メンバーと宝箱座標をもとに、マップ間の移動が最小になる最短ルートを算出し、進行を扱う。
- Mob Compassで、すべてのモブをランクや利用人数で分けず、複数の候補座標を考慮して、マップ間の移動が最小になる最短ルートを算出し、討伐進行を扱う。
- 共有周回ではリーダーが巡回ルートと進行を管理し、参加者へのチャット案内と、その案内を使った別のリーダーによる管理継続を支援する。
- 巡回に必要な地図、移動拠点、モブ、位置情報を整備できる状態を保つ。

### v1対象外

- 参加者向けの閲覧モードや共有画面。
- 共有状態の同期や共同編集。
- 編集権限を移す明示的な引継ぎ機能。
- 常設コミュニティやFCの管理。
- 高度な権限管理。
- 長期的な周回履歴や統計分析。

## 5. 責任境界・判断原則

- プロダクトは、利用者が入力・選択した情報をもとに巡回を支援する。実際のゲーム状態を自動取得・判定する責任は持たない。
- 対象の登録、ルートの採用、完了の消し込み、チャットでの伝達は利用者が行う。
- Treasure CompassとMob Compassは巡回支援の考え方を共有するが、メンバーと座標の1対1、モブと座標の1対多という違いを失わせる共通化はしない。
- モブのランクや個人利用・共有周回という使い方によって、登録後の討伐対象を別の仕組みに分けない。
- 確定した地点、候補となる地点、利用者が確認した地点を同じ意味として扱わない。
- マスターデータと利用者の周回中の情報を混在させない。
- 共有周回の管理はリーダーに限定し、参加者への伝達はチャットに委ねる。

## 6. 成功状態

- Treasure Compassで、メンバーごとの宝箱を登録し、マップ間の移動が最小になる最短ルートを確認しながら、完了まで進行を管理できる。
- Mob Compassで、一つのモブに対応する複数の座標を考慮しつつ、登録されたモブをランクや利用人数で分けず、マップ間の移動が最小になる最短ルートと討伐進行を管理できる。
- 個人利用でも共有周回でも同じ巡回支援を利用でき、共有周回ではリーダーが参加者へチャットで案内し、別のリーダーがその案内から管理を続けられる。
- Treasure CompassとMob Compassで共通する領域を活用しながら、対象と座標の対応関係の違いを保てる。

## 7. 要件定義への引継ぎ

- Treasure CompassとMob Compassで、利用者は何を入力・選択し、何を確認し、どのように完了を記録するか。
- メンバーと宝箱座標の同時点での1対1、およびモブと座標の1対多を、利用者から見える情報としてどう扱うか。
- 一つのモブに複数の候補座標がある場合、どのような条件で巡回先を選び、マップ間の移動が最小になる最短ルートを決めるか。
- 異なるマップへの移動をどのように数え、移動が同数になる候補では、テレポにかかるゲーム内通貨とロード時間、および地図、移動拠点、高さ、移動負荷を、最短ルートの評価へどのように反映するか。
- 対象の追加、削除、重複、順序変更、完了によって、巡回順と進行をどう変化させるか。
- 空、不正、不完全、未知の入力やマスターデータを、どこまで受け付け、利用者へどう伝えるか。
- 討伐リストと進行状態のうち、何をどの期間保存するか。
- 参加者向けチャット案内には何を含め、別のリーダーによる取り込みが成立したとどう判断するか。
- 古い、欠落した、または不正なチャット案内を取り込もうとした場合、どう扱うか。
- マスターデータを誰が作成・確認・更新・公開し、出典と画像利用条件をどう管理するか。
