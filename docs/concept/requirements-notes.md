# Treasure Compass / Mob Compass 要件定義以降への検討メモ

| 項目 | 内容 |

| 用途 | コンセプトから取り除いた詳細を、要件定義以降で再検討するために一時保管する |

この別紙は、[Treasure Compass / Mob Compass コンセプト](./concept.md)をコンセプトの抽象度へ整理する際に退避した情報である。内容には、会話で示された方向、既存実装から確認した事実、未決定事項、リスクが混在する。要件定義以降で上流資料と再照合し、採用、変更、破棄を判断する。

## 1. 現行Treasure Compassから確認した情報

- READMEでは、グレード別データ、手動入力またはパーティーチャットの一括入力、テレポートコストを考慮したルート計算、マップ表示、進捗管理、localStorageへの一部保存が確認できる。
- 一人のメンバーが複数の地図を持つ場合もあるが、地図は一つずつ開封されるため、同時に同じメンバーから二点以上の宝箱座標が提示されることはない。
- 周回開始後に次の地図を開封し、新しい宝箱座標を扱う場合がある。

## 2. 入力と対象データの検討事項

- 宝箱とモブの入力・選択方法、入力上限、解析できない情報の扱い。
- Treasure Compassにおけるメンバー名と宝箱座標の同時点での1対1、および地図を順次開封した際の次の座標の扱い。
- Mob Compassにおけるモブ名と座標の1対多、候補範囲、複数範囲、複数地点、利用者が確認した発見地点の扱い。
- モブの登録、討伐リストへの計上、重複、不明情報、発見情報の確定条件。
- デイリーやウィークリーをまとめて完了またはクリアする場合の扱い。
- 空、不正、不完全、重複、未知の入力やマスターデータを、どこまで受け付け、利用者へどう知らせるか。

## 3. 巡回順と進行の検討事項

- エーテライトを起点とし、高さを含む移動負荷と、既存マスターデータの `time` が表すエーテライトから外へ出やすいかどうかの重みを考慮する案がある。
- 単純な平面距離ではなく、実際の移動しやすさを含む重み付きの経路を目指す案がある。
- Treasure Compassでは一つの対象に一つの確定座標が対応する一方、Mob Compassでは一つのモブに複数の候補座標が対応するため、候補地点の選択を含む計算が必要になる。
- 手動で変更した順序を維持し、明示的な最短ルートソートを行った場合だけ計算結果へ戻す案がある。
- 周回途中に追加されたポイントは既存順序を再計算せず、末尾へ追加する案がある。
- 対象の追加、削除、完了、再計算、手動順序の変更時に、既存順序と完了済み情報をどう扱うかを決める必要がある。
- 完了単位をモブとし、候補地点や討伐数ではなく、利用者がモブを消し込んだ時点で完了とする案がある。

## 4. チャット案内とリーダー交代の検討事項

- 共有周回ではリーダーだけが討伐リスト、巡回ルート、進行を管理し、参加者にはチャットで知らせる。
- チャット案内は、利用者が出力した時点の巡回ルートと進行を示す。
- 別の利用者がチャット案内をコピー＆ペーストし、自身の管理対象として周回情報を取り込む。
- チャット案内へ含める情報、入力形式、取り込みの成立条件を決める必要がある。
- 古い案内、欠落した案内、不正な案内、重複した取り込みをどう扱うかを決める必要がある。
- 案内の出力後に元のリーダーが進行を更新すると、新旧リーダーの管理内容が一致しない可能性がある。
- ゲーム内チャットへの実際の投稿は利用者が行う。

## 5. 保存と公開の検討事項

- Treasure CompassとMob Compassの具体的なURLは固定しない。
- 既存Treasure Compassの保存データをMob Compassへ引き継がない案が記録されている。保存対象、互換性、破損データの扱いとともに再確認する。
- Mob Compassを個人サーバー上で公開する案が記録されている。公開先と公開手順は再確認する。
- 利用者の周回データとマスターデータを分離する。

## 6. マスターデータ整備の検討事項

- 対象候補は、エリア、地図、移動拠点、モブ、出現範囲、出現候補地点である。
- ページ管理者が、新パッチに合わせた追加・更新、内容確認、誤情報の訂正を担う案がある。
- データの構造、検証、編集、レビュー、履歴、保存形式、公開手順、更新責任を決める必要がある。
- 参考資料、地図、画像の出典、利用条件、更新・訂正手順を確認する必要がある。

## 7. 主なリスク

- 出現範囲、候補地点、発見地点の誤りや古さにより、利用者が誤った場所を巡回する可能性がある。
- 複数マップ、テレポート、候補範囲を組み合わせた巡回順が、実際の状況に合わない可能性がある。
- 高さや `time` が実際の移動負荷を適切に表さない可能性がある。
- 一般モブの複数地点からどの候補を採用するかによって、算出結果が実際の巡回に適さない可能性がある。
- 周回途中の追加や順序変更で、完了済み・未完了の認識がずれる可能性がある。
- チャット案内の古さや欠落により、新しいリーダーが正しい巡回ルートと進行を取り込めない可能性がある。
- マスターデータの公開前確認が不十分な場合、複数の用途へ誤情報が広がる可能性がある。

## 8. 採用しないと決定した構想

以下は要件候補ではない。過去の検討内容を誤って復活させないために記録する。

- 参加者向けの閲覧モードまたは共有画面。
- サーバー上の共有状態を参加者が参照する仕組み。
- 引継ぎIDや編集権限移譲による明示的な引継ぎ。
- 共有状態の24時間保持、再接続、同期。
