## 1. 適用範囲と責任境界

### 1.1 適用範囲

本仕様は、Treasure Compass と Mob Compass を別の公開単位として提供する v1 の外部挙動を定める。両プロダクトは、利用者が登録または選択した巡回対象を、地図と移動情報に対応付け、異なるマップへの移動を抑えた巡回順と進行を確認できるようにする。[REQ-F-001][REQ-F-002][REQ-F-006][REQ-F-007]

Treasure Compass はメンバーと宝箱座標の同時点 1 対 1、Mob Compass はモブと候補座標の 1 対 多を扱う。両者の外部上の違いを保ち、片方の対象をもう片方の対象として解釈しない。[REQ-F-001][REQ-F-003][REQ-F-004]

### 1.2 v1 の対象外

次の機能・責任は本仕様の対象外である。

- 参加者向けの閲覧画面、共有 URL、共有画面。
- リアルタイムの状態同期、共同編集、明示的な編集権限移譲。
- アカウント、ログイン、高度な権限管理、常設コミュニティまたは FC 管理。
- 長期的な周回履歴、統計分析、通知。
- ゲームクライアントとの連携、ゲーム状態の自動取得・自動判定。
- ゲーム内チャットへの自動投稿。
- サーバー上の共有状態、引継ぎ ID、再接続または同期を用いた管理継続。

これらを提供しないことは、共有周回の管理主体をリーダーに限定し、参加者への伝達を利用者のチャット操作に委ねるという責任境界の一部である。[REQ-F-010][REQ-S-001][REQ-S-003][REQ-S-004]

### 1.3 外部主体

| 主体 | 本仕様での責任 |
| --- | --- |
| Treasure Compass 利用者 | メンバー、宝箱座標、順序、完了を登録・確認・操作する |
| Mob Compass 個人利用者 | モブ、候補地点、確認、順序、完了を登録・確認・操作する |
| 共有周回のリーダー | Mob Compass の対象集合、ルート、進行を管理し、案内を出力する |
| 別のリーダー | 出力済みのチャット案内を自身の Mob Compass の管理へ取り込む |
| 参加者 | リーダーからチャット案内を受ける関係者。v1 の直接利用者ではない |
| マスターデータ管理者 | 地図、移動拠点、モブ、位置情報、出典、利用条件を整備・確認・訂正・公開する |

利用者が登録、ルート採用、地点確認、完了、チャット伝達を明示的に行う。プロダクトは、ゲーム内で実際に討伐・開封・移動が行われたことを自動で事実化しない。[REQ-S-001][REQ-S-002][REQ-S-003]

## 2. 用語と外部状態の意味

| 用語 | 外部上の意味 |
| --- | --- |
| 対象 | 現在の周回で利用者が登録した、Treasure の宝箱対象または Mob のモブ対象 |
| 現在の対象集合 | 削除されておらず、利用者の周回情報として保持されている対象の集合。完了対象を含む |
| 有効対象 | 必須情報と参照先が検証済みで、ルートまたは進行の対象にできる対象 |
| 未確認対象 | 入力またはマスターの不足・未知・不正などにより、正しい対象または地点と確定できない対象 |
| 地図 | 対象地点が属するマップ。表示名と、ルート比較で同一性を判定する識別情報を持つ |
| 移動拠点 | マップへ移動するためにマスターデータが提供する拠点。テレポに伴う移動負荷の評価対象となり得る |
| 確定地点 | マスターデータ管理者が確定情報として公開した地点。利用者の確認やルート採用を意味しない |
| 候補地点 | マスターデータまたは利用者入力が可能性として示す地点。モブの存在や利用者の確認を意味しない |
| 候補集合 | 一つの Mob 対象に対応する、ルート候補として識別できる候補地点の集合 |
| ルート採用地点 | 現在の自動算出ルートが、その Mob 対象を訪れる地点として選んだ候補地点 |
| 利用者確認地点 | 利用者が、その地点を確認したと明示的に記録した地点。ルート採用やモブ完了とは別の意味を持つ |
| 完了対象 | 利用者が対象について完了操作を行った対象。地点確認、候補採用、ゲーム状態の自動判定とは異なる |
| 自動ルート | 現在の対象集合から仕様の評価規則により算出された順序 |
| 手動順序 | 利用者が明示的に並び替えた現在の順序。自動ルートとは区別して表示する |
| 案内スナップショット | リーダーが出力した時点の Mob Compass の対象、ルート、候補、確認、完了、順序を表す一回分の情報 |

地点の意味は、状態表示上のラベル、凡例、またはそれと同等に利用者が識別できる方法で区別する。単に地図上へ描画されたこと、ルートに含まれたこと、入力されたことだけで別の意味へ昇格させない。[REQ-F-004][REQ-F-007][REQ-F-009][REQ-F-014]

## 3. 共通の入力・出力契約

### 3.1 利用者が提供する情報

v1 は、Treasure と Mob の一件ずつの手動入力、Mob Compass の通常の複数行入力、Treasure の既存パーティチャットの複数行貼り付け、マスターデータからの選択、およびマップ上の地点選択を入力経路として扱う。共有周回の正式な管理継続だけは、8 章の Mob Compass 案内取り込みを用いる。物理的な入力欄、ダイアログ、ボタンの構成は Design で決めるが、受理される意味は以下に限る。[REQ-F-002][REQ-D-001]

| 情報 | 必須性と用途 |
| --- | --- |
| プロダクト種別 | 必須。Treasure の入力を Mob の対象へ、または Mob の入力を Treasure の対象へ解釈しない |
| Treasure のグレード | 対応する地図マスターデータを選択するために必要な場合は必須。対応する地図集合が特定できなければ登録しない |
| メンバー名 | Treasure の必須識別情報。空白だけは不可。登録後の同一周回では、正規化後に同じ名前を同一メンバーとして扱う |
| モブ名 | Mob の必須識別情報。空白だけは不可。直接入力で未知のモブ名は有効な Mob 対象にしない。構文上有効な案内/保存から未知になった場合は 8.2/9.2 の未確認規則を適用する |
| 座標 | 対象地点を特定するために X/Y を必須とする。値はゲーム内で表示されるマップ座標であり、画像上のピクセル座標ではない。マスターデータが高さ等を必須項目として定める地点では、それも必須とする |
| マップ | 座標と組み合わせて必須。直接入力ではマスターデータが定める正規識別子または登録済みの正規別名だけを受理し、未知のマップ、対象種別・グレードと対応しないマップは受理しない。構文上有効な案内/保存から未知になった場合は未確認として保持する |
| 移動拠点 | 利用者が特定の移動拠点を選択する場合に使用する。未選択時は、対象マップについてマスターデータが提供するすべての有効な拠点を、マップ間遷移が必要なルート候補の選択肢として扱う。マップ間遷移に必要な有効な拠点が一つもない場合は、そのルート候補を採用しない |
| 候補地点 | Mob で任意。既知のモブに複数地点を登録する場合、同じモブの候補集合へ追加する。Treasure では候補地点として扱わない |
| 利用者確認 | Mob で任意。利用者が地点を確認したことだけを記録し、ルート採用や完了を同時に成立させない |
| チャット案内 | Mob の管理継続に使う場合に任意。8 章の案内契約を満たす一つの平文ブロックとして扱う |

座標の外部契約は次の通りとする。入力・表示・ルート結果で用いる座標はゲーム内マップ座標であり、画像座標と同一視しない。X/Y は有限の非負十進数で、入力として受理する表記は ASCII 数字列 `0` 以上の整数部と、任意の 1 桁以上の小数部（例: `12`、`12.3`、`12.34`）とする。先頭の `+`、負号、指数表記、カンマ、全角数字・全角記号、整数部のない `.5`、小数部のない `12.` は受理しない。受理値は十進数として小数第 1 位へ四捨五入（小数第 2 位が 5 以上なら繰り上げ、それ以外は切り捨て）して正規化し、整数は `12.0` とする。正規化後の座標は選択したマップのマスターデータが公開する有効範囲内でなければならない。画面上の座標表示と同一性判定はこの正規化値を小数第 1 位で用いるため、たとえば `12.04` と `12.0` は同一地点として扱う。マスターデータ上の画像座標との変換は実装上必要な場合に Design / Implementation で定めるが、利用者へ返す座標の意味と表示値は変えない。[REQ-D-001][REQ-D-007]

対象名、メンバー名、モブ名、マップ名および移動拠点名は、Unicode の前後空白を除去し、Unicode NFC へ正規化してから照合する。内部空白、大小文字、全角/半角の別は保持し、推測による表記揺れ変換や部分一致を行わない。空になった値、改行または制御文字を含む値は受理しない。マップ、モブ、移動拠点の照合は、マスターデータが公開する正規識別子または正規別名との完全一致に限る。[REQ-D-001][REQ-D-007]

### 3.2 入力経路と原子性

- 手動入力は、Treasure では一つの対象、Mob では一つのモブと一つの地点を明示して登録する経路である。必須項目が揃わない入力は登録しない。[REQ-F-002][REQ-F-004][REQ-D-001]
- Mob Compass の通常の複数行入力は、正式なリーダー引継ぎ案内とは別の入力経路であり、次の一行形式だけを受理する。

  ```text
  mob: <モブ名> | <マップ識別子または登録済み正規別名> | <X>,<Y>
  ```

  行頭の `mob: `、二つの ASCII の ` | `、および X/Y 間の一つの ASCII カンマを構文上の区切りとする。各フィールドは 3.1〜3.3 の文字列・座標契約で検証し、フィールド値の `|`、改行、制御文字、percent-encoding による別表現は受理しない。空行は無視し、非空行は一行を一つのモブ・地点入力単位として独立に解析する。形式とマスター参照を満たす行だけを現在の Mob 対象へ追加し、拒否行は既存の対象、候補集合、順序、確認、完了を変更しない。同じモブに別の有効地点があれば同じモブの候補集合へ追加し、同じモブ・正規マップ識別子・正規化座標なら重複として候補を増やさず、既存候補の確認、採用、完了も変更しない。通常の複数行入力で受理した地点は候補地点として扱い、確認地点、ルート採用地点、完了対象へ自動的に昇格させない。受理件数、拒否件数、拒否理由、重複を利用者が区別できるようにする。

  `MOB-COMPASS/1` で始まるブロック、`run`、`revision`、`item`、`candidate` 等の案内行は、この通常形式の行として解釈しない。通常の複数行入力へ混在した場合も、`mob: ` 形式を満たさない行として拒否し、8.2 の案内取り込みによる部分的な解釈を行わない。[REQ-F-004][REQ-D-001][REQ-D-007]
- Treasure のパーティチャット貼り付けは、空行を無視し、非空行を `<半角または全角の開き括弧><指定記号または省略><メンバー名><半角または全角の閉じ括弧><1 個以上の空白><マップ名><1 個以上の空白><半角または全角の開き括弧><X><空白任意><半角または全角のカンマ><空白任意><Y><半角または全角の閉じ括弧>` の形式として受理する。指定記号は `★☆●▲◆♥♠♣◇♦♡○□△▽` のいずれか 1 文字または省略とし、メンバー名、マップ名、X/Y は 3.1〜3.3 の契約で検証する。行全体からこの形式を一意に解釈できない場合はその行を拒否する。
- 複数行入力は各行を独立した入力単位として解析し、受理された行だけを現在の対象集合へ追加する。拒否された行は登録せず、既存の対象、順序、完了、確認を変更しない。受理件数、拒否件数、拒否理由を利用者が区別できるようにする。貼り付け操作が受理済みの行を現在集合へ追加できない場合は、その操作全体を拒否する。
- Mob のマスターデータからの選択は、既知のモブ一つと、そのモブに対応するマスター上の地点一つを一組として登録する。マスター由来の確定/候補の意味は保持し、同じモブについて別の地点を選択した場合は同じ Mob 対象の候補集合へ追加する。マスターにないモブ・地点はこの経路から登録しない。[REQ-F-004][REQ-F-013][REQ-D-001]
- Mob のマップ上の地点選択は、選択したモブに対応する現在のマスターデータ上の有効な地点だけを候補地点として登録する。地図画像上の任意位置を、対応するモブまたは地点として推測登録しない。[REQ-F-004][REQ-D-001][REQ-D-007]
- チャット案内の取り込みは、8.2 の一つの案内スナップショットを単位とし、必須情報が欠けた案内を部分的に登録しない。
- Treasure のマップ上の選択は、選択された地点が現在のマスターデータの有効な地点である場合だけ受理する。地図画像上の任意位置を、対応する地点として推測登録しない。
- 空入力は対象を追加せず、既存の対象集合、順序、完了、確認、保存情報を変更しない。
- v1 は対象数、候補数、入力行数について製品横断の数値上限を設けない。実行環境の容量不足等で要求全体を受理できない場合は、その操作全体を拒否して既存状態を変更しない。入力行を独立処理する複数行入力では、形式上受理できる行だけを登録し、拒否行を明示するという 3.2 の原子性を適用する。[REQ-D-001][REQ-D-007]

### 3.3 正規化、重複、未知値

上記の正規化後の文字列と、座標の正規化値を同一性判定に用いる。利用者が入力した値を表示する場合は、正規化後の意味を識別できる形で表示し、入力を HTML として解釈しない。数値・座標の形式、マップ参照、対象名参照が検証できない場合は拒否し、既存の有効対象へ推測変換しない。マスターデータの更新後に既存参照が解決できなくなった場合だけは、9.2 および 10.2 に従う未確認状態として保持する。[REQ-D-001][REQ-D-007]

同一周回・同一プロダクトにおける重複は次のように扱う。

| 重複または衝突 | 外部結果 |
| --- | --- |
| 同じ対象識別情報、マップ、座標、順次位置を再入力 | 新しい対象を増やさず、既登録であることを知らせる。既存の順序・状態を変更しない |
| Treasure で同じメンバーの現在対象を、次の地図として示さず再入力 | 現在対象を置き換えず、衝突として拒否する |
| Mob で同じモブに同じ地点を再入力 | 候補集合を増やさず、既登録であることを知らせる |
| Mob で同じモブに別の有効な地点を入力 | 別モブ対象を作らず、そのモブの候補集合へ追加する |
| 同名だが地点または順次位置が異なる Treasure 対象 | 同一メンバーの同時対象にはせず、次の地図の明示入力がなければ拒否する |
| 未知の対象、未知のマップ、対応しないグレード | 有効対象として登録しない。利用者が入力を修正できる識別可能な結果を示す |

重複判定における「同じ」は、正規化後のプロダクト、対象識別情報、順次位置、候補識別、正規マップ識別子、正規化座標がすべて一致することをいう。Mob の候補集合は候補識別をキーとして扱い、候補集合内の順序は意味を持たない。拒否または重複の通知は、成功した登録、ルート再計算、完了更新として数えない。[REQ-F-003][REQ-F-004][REQ-F-008][REQ-D-007]

## 4. Treasure Compass 外部仕様

### 4.1 メンバーと宝箱座標

Treasure の一つのメンバーは、ある時点で一つの現在宝箱座標だけを持つ。現在宝箱座標は、メンバー名、選択したグレードの地図、座標を利用者が対応付けて確認できる一つの対象である。別メンバーの対象と結合したり、一つの座標を複数メンバーへ暗黙に複製したりしない。[REQ-F-003]

一人が複数の地図を持つ場合、次の地図を開封したことを利用者が明示して新しい座標を入力または選択したとき、その座標は同じメンバーの「次の順次対象」として受理できる。次の順次対象は現在対象とは別の時系列上の対象であり、現在対象と同時に現在地点として表示・算出しない。現在対象が完了または削除された後、次の対象がそのメンバーの現在対象になる。[REQ-F-003][REQ-F-008]

現在対象が残ったまま、次の地図であることを示さない別座標を同じメンバーへ追加する操作は、1 対 1 の制約に反するため受理しない。プロダクトは、既存対象を上書きせず、利用者へ衝突を示す。[REQ-F-003][REQ-D-007]

### 4.2 Treasure の操作結果

| 操作 | 外部結果 |
| --- | --- |
| 有効なメンバー・座標を登録 | 現在の対象集合へ追加し、メンバーと座標、地図、完了/未完了を表示する。自動ルート中なら更新後集合で再算出する |
| 次の地図を登録 | 同じメンバーの順次対象として表示し、現在対象とは区別する。前の対象が完了または削除された後に巡回対象へ移る |
| 対象を削除 | 対象を現在の対象集合から除外し、完了や順序をその対象について以後のルートへ反映しない。削除はゲーム内で未完了だったことを意味しない |
| 対象を完了 | 利用者が完了したことを記録し、未完了対象と区別する。ゲーム状態、地点確認、ルート採用を自動成立させない |
| 完了を解除 | v1 の必須操作とはしない。完了済み情報は利用者が明示的に削除・再登録するまで完了として保持し、自動的に未完了へ戻さない |
| 並び順を手動変更 | 現在の表示順を手動順序として扱い、自動ルートとは別に表示する |
| 次の対象が現在対象になる | 新しい座標を同じメンバーの現在対象として表示し、その対象を未完了としてルート対象へ含める |

同一メンバーの次の順次対象が複数保留される場合も、順番を保持し、一度に一つだけを現在対象へ昇格させる。保留中の順次対象を現在対象と誤認させない。[REQ-F-003][REQ-F-007][REQ-F-008][REQ-F-009]

## 5. Mob Compass 外部仕様

### 5.1 モブと候補集合

Mob の一つのモブ対象は、モブ名と、そのモブについて現在利用できる候補地点の集合を持つものとして利用者に表示する。一つの候補地点を別のモブ対象として数えず、同じモブの候補を別々の完了単位にしない。[REQ-F-004]

候補地点は、次のいずれかとして表示される。

- マスターデータ管理者が確定情報として公開した確定地点。
- マスターデータまたは利用者入力が可能性として示した候補地点。
- 現在の自動ルートがそのモブの訪問先として選んだルート採用地点。
- 利用者が地点を確認したことを明示した利用者確認地点。

これらは同じ地点に同時に成立し得るが、表示上の意味は併記して区別する。たとえば、確定地点がルート採用されても、それだけで利用者確認地点や完了対象にはならない。候補地点が利用者確認された場合も、候補であった事実を失わせず、モブ完了にはしない。[REQ-F-004][REQ-F-007][REQ-F-009]

候補識別は、正規マップ識別子と正規化後の X/Y からなる地点識別であり、同じモブ内で同じ地点を一意に指す。マスターデータ由来の確定/候補の意味と、利用者周回上の採用/確認/完了の意味は別々に表示する。マスターデータの更新で地点を解決できなくなった場合も、最後に記録された候補識別を推測変更せず、未確認として表示する。[REQ-F-004][REQ-F-013][REQ-F-014]

### 5.2 複数候補と採用地点

未完了かつ有効な Mob 対象について、ルート算出はその候補集合から訪問地点を一つ選ぶ。候補集合の全地点を別々の訪問先として必ず巡回するのではなく、一つのモブを一度の対象として扱う。候補地点のうち、マップ、座標、移動拠点その他の必要情報が検証できないものは、その候補の計算から除外し、未確認として表示する。少なくとも一つの有効候補が残る Mob はその候補だけで算出対象にできるが、有効候補が一つもない Mob は全体の自動ルートを成立させない。[REQ-F-004][REQ-F-006][REQ-D-007]

採用地点はルート結果の各モブ行および、該当するマップ表示から識別できる。識別には、モブ名に加え、候補地点を他の候補と区別できる正規マップ識別子と正規化座標を用いる。採用地点の識別は利用者の確認・完了を意味しない。自動ルートの更新で採用地点が変わった場合は、現在の採用地点と、前回の採用地点を履歴として混同させず、利用者確認地点が別候補に残っていることも識別できる。[REQ-F-004][REQ-F-007]

候補の組み合わせと対象順序を比較した結果、第一評価が同じで、補助評価によって他候補に優越されない候補が複数残る場合、以下を外部結果とする。

1. ルートは一つの表示順として提示するが、該当するモブの採用地点に「同順位」であることを表示する。
2. 同順位候補のマップ、座標、評価に用いた移動負荷を利用者が比較できるようにする。いずれか一つを優れていると表示しない。
3. 一つの表示順を安定させるための最終的な並びは、評価軸ではない決定的な表示規則で定める。ルートの訪問順に並ぶ各地点について、正規マップ識別子を ASCII 辞書順、X/Y を数値順、対象識別情報を Unicode code point 順で比較し、そのタプル列を辞書順に比較する。この表示規則は料金、ロード時間、距離その他の新しい優先軸ではない。

同順位の場合も、決定的な表示順の先頭を現在の自動ルートが採用した地点として識別できるが、同順位であることを併記する。これはルート結果上の採用であり、利用者確認、ゲーム内の存在確認、モブ完了を成立させない。候補の並び順が安定していることだけで、同順位の他候補が採用されたことや利用者が地点を確認したことにはならない。[REQ-F-004][REQ-F-006][REQ-F-007]

### 5.3 利用者確認とモブ完了

利用者が候補地点を確認する操作を行うと、その地点は利用者確認地点として表示される。確認地点が自動ルートの採用地点である場合は両方の印を表示し、別の候補である場合は採用地点と確認地点を別々に表示する。確認操作は、別候補へのルート変更、モブ完了、他の候補の削除を自動的に行わない。[REQ-F-004][REQ-F-009]

利用者がモブを完了すると、モブ対象全体が完了済みになる。完了は候補地点単位ではなくモブ単位であり、候補の採用、候補の存在、利用者確認だけから自動完了にしない。完了したモブは未完了の自動ルート算出から除外するが、そのモブに属する候補地点、採用・確認の記録は周回情報として識別可能な状態で保持する。[REQ-F-004][REQ-F-007][REQ-F-009]

完了済み Mob に候補地点を追加しても、完了状態は解除せず、その候補を未完了ルートへ自動追加しない。完了済み Mob を再び巡回対象にする訂正は、7.3 の削除・再登録による利用者操作で行う。完了済み Mob の候補集合に含まれる地点は、完了済み対象の候補として引き続き表示する。[REQ-F-008][REQ-F-009]

Mob Compass は、モブのランク、個人利用か共有周回か、利用人数によって、登録後の対象単位、候補集合、完了単位、ルート評価の扱いを分岐させない。[REQ-F-005][REQ-F-010]

## 6. ルート算出と表示

### 6.1 算出対象

自動ルートは、現在の対象集合のうち、未完了で、必須情報および参照先が検証済みの対象を、各対象一回ずつ巡回する順序として算出する。完了済み、削除済み、未確認、計算に必要な情報が欠落した対象は、自動ルートの有効な訪問先に含めない。ただし、現在の対象集合、完了対象、未確認対象としての表示からは隠さない。[REQ-F-006][REQ-F-007][REQ-F-009][REQ-D-007]

Treasure は各有効対象の一つの現在座標を比較する。Mob は各有効モブについて候補集合から一つの候補を選び、候補の選択と対象順序、マップ間遷移が必要な場合の移動拠点の選択を一体のルート候補として比較する。利用者が移動拠点を指定した場合はその拠点だけを用い、指定しない場合は対象マップの有効な拠点を候補に含める。候補地点を持たない、または有効候補が一つもないモブはルートを成立させず、未確認・計算対象外として表示する。[REQ-F-004][REQ-F-006][REQ-D-001]

### 6.2 評価の順序

ルートの評価は、次の順序を外部契約とする。

1. 順序中の隣り合う対象のマップが異なる回数を数え、その回数が最小の候補を残す。同一マップ内の地点間移動は、この第一軸の遷移には数えない。第一対象へ到達する移動や巡回終了後の帰還も、対象集合間の遷移回数には含めない。
2. 第一軸が同じ候補について、各マップ間遷移に必要なゲーム内通貨の合計とロード時間の合計を比較する。合計は、候補が選んだ移動拠点のマスターデータ上の値を、対象集合間の各遷移について加算した値とする。通貨合計とロード時間合計の両方が他候補以下で、少なくとも一方が他候補より小さい候補は、他候補より優先する。片方だけが小さく他方が大きい候補同士は優劣を付けず、通貨だけの順位付け、ロード時間だけの順位付け、任意の重み付け合算、評価軸としての辞書順比較を行わない。
3. 補助評価で優越されなかった候補が複数残る場合は同順位として扱い、6.3 の同順位結果を返す。補助評価は第一軸の差を覆さない。

料金またはロード時間の情報が存在しない場合、存在する一方だけで優劣を決めない。第一軸の最小候補が一つだけなら、その候補を返し、欠落した補助値を「未提供」と表示する。第一軸の最小候補が複数あり、比較に必要な通貨またはロード時間が一つでも欠落・不正なら、単一の採用地点を決めず「補助値不足による計算不能」として該当候補を表示する。値が揃っている場合は、上記の二つの合計値による優越関係だけを適用する。[REQ-F-006][REQ-D-007]

通貨の単位、ロード時間の単位、値が適用される遷移、移動拠点ごとの値は、マスターデータが利用者に識別できる形で公開する。ルートの外部比較規則は本節で確定し、経路探索アルゴリズム、探索方法、グラフ表現、最適化、内部スコア表現およびデータ構造は Design に残す。[REQ-F-006][REQ-F-013][REQ-S-005]

### 6.3 ルート結果

算出成功時、利用者は少なくとも次を同時に確認できる。

- 算出の対象となった現在の有効対象集合。
- 巡回順、各対象の名前、メンバー名またはモブ名、マップ、座標。
- 異なるマップへの遷移回数。
- Treasure の同一メンバーの順次対象の関係。
- Mob の候補集合、現在のルート採用地点、利用者確認地点、確定/候補の意味。
- 完了済み、未完了、未確認、計算対象外の区別。
- 自動ルートか手動順序か、および同順位が残った場合の表示。

同順位が残る場合も、単一の結果を返したことだけで一意の最適性を主張しない。利用者が同順位の候補を識別できる情報を表示する。[REQ-F-006][REQ-F-007]

同順位候補を一つの表示順へ配置する必要がある場合、5.2 のタプル列の比較で安定させる。この規則は同順位候補を利用者に提示するための表示規則であり、料金、ロード時間、地点間距離その他の新しい評価軸ではない。表示順の先頭に置かれた候補を、他候補より優れたものまたは利用者が確認したものとして扱わない。[REQ-F-006][REQ-F-007]

空の現在対象集合にはルートを表示せず、空状態を表示する。未完了の有効対象がない場合は、全対象完了またはルート対象なしとして表示し、完了済み対象の一覧は区別して確認できる。対象が一つだけの場合の遷移回数は 0 とする。[REQ-F-007][REQ-F-009]

### 6.4 計算不能と再算出

計算不能は、たとえば必要な地図、座標、移動拠点、候補地点が欠落・不正である場合、補助値による比較が必要なのに料金またはロード時間が欠落・不正である場合、または現在対象集合を比較可能な候補へ変換できない場合に成立する。未完了の現在対象に一つでも有効な地点がない場合は、対象の一部だけを「全対象の自動ルート」として返さず、自動ルート全体を未算出とする。計算不能時は、失敗理由と該当対象を利用者が識別できるようにし、計算不能な情報を含めた成功ルート、完了更新、採用地点の確定を返さない。[REQ-D-007][REQ-S-001][REQ-S-002]

有効な対象集合が変化した場合、自動ルート表示は更新後の集合だけを入力にして算出された結果へ置き換える。古い結果を現在の結果として残さず、更新中は現在の集合と再算出中/未計算の状態を識別できるようにする。計算に失敗した場合も、既存の完了・確認・登録情報と各 Mob の最後に成功した採用地点の記録を破棄せず、失敗したルートだけを無効として表示する。ただし、最後に成功した採用地点は現在の自動ルートとして表示せず、手動順序で参照できる過去の採用地点として識別する。[REQ-F-008][REQ-F-009][REQ-D-007]

## 7. 進行、手動順序、ライフサイクル

### 7.1 自動ルート中の操作

自動ルートを表示しているときの操作結果は以下とする。

- 有効な対象の追加後、更新後の未完了対象集合から自動ルートを再算出し、新規対象、変更後の遷移回数、順序を利用者が確認できる。
- 対象の削除後、削除対象を除く更新後集合から再算出し、削除対象をルートや残数に含めない。
- 対象の完了後、完了対象を自動ルートから除外し、残りの未完了対象を再算出する。完了対象は完了一覧に保持する。
- 重複または拒否された入力後は、対象集合、順序、完了、確認を変えず、再算出しない。
- 次の地図の対象が追加された場合は、対象の順次関係を表示したうえで、その対象が現在対象となった時点から自動ルートへ含める。

### 7.2 手動順序中の操作

利用者が順序を手動変更した後は、現在の順序を手動順序として表示し、自動算出された順序であると表示しない。手動順序についても、その順序のマップ間遷移回数を表示できるが、自動ルートの最小性を主張しない。[REQ-F-008][REQ-F-007]

手動順序中に有効な対象を追加した場合、新規対象は既存の手動順序を壊さず、未完了の手動順序の末尾へ追加する。削除は該当対象だけを除き、残りの手動順序を保持する。完了は該当対象を未完了の巡回順から除くが、完了一覧で識別できるようにする。次の地図の対象も同じ規則で、現在対象になった時点で手動順序の末尾へ加える。[REQ-F-008][REQ-F-009]

手動順序への変更は対象順だけを変更し、Mob の候補地点の採用を自動的に変更しない。各 Mob のルート採用地点は、最後に成功した自動算出で選ばれた地点を表示し、新規 Mob にまだ採用地点がない場合は候補集合と未確認を表示する。その Mob は手動順序上で識別できるが、候補地点の採用が成立するまでは計算済みの地点として扱わない。利用者が「最短ルートを再計算」すると、全ての未完了・有効な Mob の候補集合を再評価し、採用地点を更新する。[REQ-F-004][REQ-F-008][REQ-F-009]

手動順序のマップ間遷移回数は、手動順序に並ぶ各対象について一つの地点が外部上確定している場合だけ算出する。Mob に最後に成功した自動算出の採用地点があり、その地点が現在のマスターデータでも有効なら、その採用地点を手動順序の地点として使用する。新規 Mob のように候補集合はあるが採用地点がない場合、または採用地点を現在解決できない場合は、隣接する既知地点の一部だけを数えず、手動順序全体の遷移回数を「未確定（採用地点未選択）」として表示する。別の Mob の採用地点や、過去に最後に成功した別周回の地点を代用しない。手動順序中に候補を一つにする独立した暗黙操作はなく、数値を得るには利用者が明示的に「最短ルートを再計算」し、成功した自動算出で採用地点が定まる必要がある。[REQ-F-004][REQ-F-006][REQ-F-008]

たとえば、採用地点が Map A の Mob A、候補が Map B / Map C で採用地点のない新規 Mob、採用地点が Map D の Mob D の順に手動で並んでいる場合、Map A から新規 Mob および新規 Mob から Map D の遷移を数値化せず、手動順序全体を「遷移回数未確定」と表示する。Map B または Map C を表示順だけから選んだり、直前の Map A を新規 Mob の地点として流用したりしない。[REQ-F-004][REQ-F-006][REQ-F-008]

自動ルートへ戻る操作は、利用者が「最短ルートを再計算」または同等の明示操作を行った場合に限る。その操作は、現在の未完了かつ有効な対象集合と Mob の候補集合を再評価し、自動ルート表示へ切り替える。単なる対象追加、削除、完了、再読み込み、チャット出力は手動順序を自動ルートへ黙って切り替えない。[REQ-F-008]

### 7.3 完了と終了

完了操作は利用者の明示操作でのみ成立する。完了済み対象を再計算対象へ戻す自動解除は行わない。v1 では完了解除を独立した必須操作とせず、誤って完了した場合の訂正は、対象を削除して必要な情報を再登録する利用者操作で行う。[REQ-F-009][REQ-S-002]

すべての対象が完了した場合、アクティブな自動ルートは空となり、全対象完了を表示する。完了済み対象、完了時点の地点確認、最後に採用されていた候補地点は、周回情報として区別して確認できる。新しい対象を追加した場合は、全完了表示を解除し、現在の順序モードに従ってその対象を未完了対象として扱う。[REQ-F-008][REQ-F-009]

## 8. チャット案内とリーダー交代

### 8.1 出力契約

共有周回のリーダーは、Mob Compass の現在状態を一回分の平文スナップショットとして出力し、クリップボード等を通じて利用者がゲーム内チャットへ貼り付けられる。プロダクトはゲーム内チャットへ直接投稿しない。[REQ-F-011][REQ-D-005][REQ-S-004]

一つの案内スナップショットには、少なくとも次を含める。

- `Mob Compass` の製品識別、案内形式のバージョン、出力時点。
- 同一の論理的な周回を識別する `run`（周回識別子）。これは一回の出力を識別する値ではない。
- 同じ `run` 内の案内世代を識別する `revision`。案内の新旧・重複・競合の主判定に用いる。
- 出力時点の対象集合に含まれる各モブの名前、候補地点または採用地点のマップ・座標。
- 各モブについて、候補地点であること、確定地点であること、現在のルート採用地点であること、利用者確認地点であることの区別。
- 出力時点の自動ルートまたは手動順序、各対象の順序、マップ間遷移回数。
- 各モブの完了/未完了、および未確認・計算対象外の情報。

案内は、次の論理構成を持つ一つの平文ブロックとする。コード例の `...` は複数行を表す記号であり、実際の案内へ出力しない。クリップボードへの出力方法や内部の文字列処理は Design へ送るが、外部形式の必須要素と境界は固定する。

```text
MOB-COMPASS/1
run: <周回識別子>
revision: <世代>
issued-at: <出力時点>
mode: auto | manual
transitions: <遷移回数> | unknown
candidate: <モブ識別> | <モブ名> | <候補識別> | <マップ識別> | <X>,<Y> | <地点の意味> | <確認状態>
item: <順序> | <モブ識別> | <モブ名> | <採用候補識別> | <完了状態>
...
END-MOB-COMPASS
```

`MOB-COMPASS/1` と `END-MOB-COMPASS` は案内ブロックの開始・終了を示す。入力はこのブロック一つだけとし、境界の外側に非空の文字列がある場合、二つ以上のブロックがある場合、空行がある場合は受理しない。行末は LF または CRLF のいずれかを受理する。`run`、`revision`、`issued-at`、`mode`、`transitions`、現在の各 Mob に対する一つの `item`、および各 Mob の候補集合の各地点に対する一つの `candidate` は必須である。候補が一つもない Mob または候補地点を表現できない Mob を含む状態は、案内として出力しない。

`run` は空でない ASCII の `[A-Za-z0-9_-]+` とし、同一の論理的な周回の間、対象追加・削除・完了・並び順変更・案内再出力・別リーダーによる取り込み後の再出力で維持する。空の新規状態へ最初の Mob 対象を登録した時に周回識別子が付与される。利用者が「新しい周回」を明示して開始した場合、または異なる `run` の案内を明示的な置換操作で取り込んだ場合だけ、新しい現在周回の `run` になる。対象を全削除したこと、全対象を完了したこと、再読み込みしたことだけでは `run` を変更しない。`run` の生成方法や内部 ID 型は定めない。[REQ-F-008][REQ-F-012]

`revision` は、同じ `run` 内の案内世代を表す、先頭 0 の表記を除く非負の ASCII 十進整数（`0` または `[1-9][0-9]*`）とする。新しい `run` の最初の案内出力は `0` とし、同じ `run` の新しい案内を出力するたびに、直前に出力または受理した案内の値へ厳密に 1 を加える。案内を出力する利用者が前回値を保持していない、または次の値を確定できない場合は出力を失敗させ、状態を変更しない。取り込み時は世代の連続性を要求せず、現在値より大きい `revision` を有効な新しい案内として扱うため、途中の世代を受け取れなかった場合でも後続の案内を取り込める。取り込んだ案内を別のリーダーが再出力するときは、取り込んだ `revision` を基準に次の値を出力する。[REQ-D-005][REQ-F-012]

`issued-at` は、その案内ブロックに含める状態スナップショットの出力操作が完了した実時刻を示す。ゲーム内の討伐・移動・チャット投稿時刻、取り込み時刻ではない。値は UTC の RFC 3339 形式で、`YYYY-MM-DDTHH:mm:ss.sssZ` の 1 ミリ秒精度を必須とする。時刻として解釈できない値、UTC 以外のオフセット、秒未満の桁数が異なる値は受理しない。`issued-at` は形式と実時刻の情報として保持するが、新旧・重複・競合の判定、次の `revision` の決定、案内を出力できるかどうかには使用しない。端末時計のずれにより、前回案内より過去または同じ時刻になっても、`revision` が有効なら案内の世代順序を無効にしない。[REQ-D-005][REQ-F-012]

各行の ` | ` は唯一のフィールド区切りである。フィールド値は UTF-8 の percent-encoding とし、ASCII の unreserved 文字（`A-Z a-z 0-9 - . _ ~`）以外の各バイトを大文字の `%HH` で表す。したがって区切り文字、改行、`%` および制御文字をフィールド値へ直接含めない。デコード後のモブ名等は 3.3 の正規化を適用する。`mode` は `auto` または `manual`、`transitions` は 0 以上の十進整数または小文字の `unknown`、地点の意味は `confirmed` または `candidate`、確認状態は `confirmed` または `unconfirmed`、完了状態は `complete` または `incomplete`、採用候補がない場合は `none` とする。デコード後の `<候補識別>` は `<正規マップ識別子>@<X>,<Y>` とし、X/Y は 3 章の正規化値を用いるため、同一 Mob 内で再出力しても変わらない。`candidate` 行は候補集合の一地点を、`item` 行は各 Mob の対象・順序・採用地点・完了を表す。`order` は未完了対象の現在表示順を 1 から始めた値とし、完了対象は `-` とする。自動モードの順序は自動ルート、手動モードの順序は手動順序を表す。候補行の順序は意味を持たないが、同一候補識別の行を重複させない。`item` 行の出現順も意味を持たず、各行の `order` が対象順を表す。

必須項目のない行、未知の行種別、開始・終了境界のない断片、候補行を欠いた `item`、同じ対象または候補識別の矛盾する複数行、`revision` のない旧形式、未対応バージョン、余分な対象を含む別形式は有効な案内としない。これにより、取り込み側は製品、バージョン、周回識別子、案内世代、出力時点、対象、候補集合、採用地点、順序、完了を同じ意味で復元できる。[REQ-D-005][REQ-F-012][REQ-D-007]

### 8.2 取り込み成立条件

別のリーダーが案内を取り込むと、案内に含まれる対象と出力時点のルート・進行を、自身の Mob Compass の独立した周回情報として扱う。取り込みが成立する条件は次の通りである。

1. 製品識別が Mob Compass と一致する。
2. 対応可能な形式バージョンである。
3. 出力時点、`run`、`revision`、対象、地点、順序、完了の必須項目が揃い、各値が 8.1 の構文・正規化・行間整合性を満たす。
4. 一つの案内ブロックとして解析でき、行の欠落、改変による不整合、未知の必須値がない。
5. 既存の異なる `run` の非空周回を黙って上書きしない。その場合は、利用者が現在周回を消去・置換する明示操作を先に行う。空の現在状態への初回取り込みは、案内の `run` を現在周回の識別子として受理する。

条件を満たさない案内は部分的に取り込まず、既存状態を変更しない。不完全・不正な案内は、どの条件を満たさないかを利用者が識別できるようにする。[REQ-F-012][REQ-D-007]

構文上は有効でも、取り込み側のマスターデータにマップ、モブ、地点または移動負荷の参照が存在しない場合は、案内全体を保持したうえで該当する参照を未確認・計算対象外として表示し、その情報を自動ルートへ使用しない。取り込み側にない参照を別の名前、地点、候補へ推測変換しない。この場合も対象、順序、完了および案内の `run` / `revision` / `issued-at` は失わず、利用者がマスターデータの差異として識別できるようにする。[REQ-D-007][REQ-F-012][REQ-F-014]

### 8.3 古い案内、重複、取り込み後

同じ `run` について、現在受理済みのスナップショットがある場合は、その `revision` と比較して外部結果を次のように定める。現在の `run` にまだ案内スナップショットを受理していない場合、検証に成功した非負の `revision` の案内をその `run` の基準として受理する。取り込み側の現在時刻や `issued-at` の新旧は、この判定に使用しない。ここでいう案内全体の一致は、生の行順ではなく、8.1 の構文を検証してデコード・正規化した意味上のスナップショットで比較する。候補行と `item` 行の出現順は意味を持たず、`item` の `order` と各候補識別等の値が一致することを比較する。

- `revision` が現在値より小さい場合は「古い案内」として拒否し、現在の対象、ルート、進行、周回識別子、`revision`、`issued-at` を変更しない。
- `revision` が現在値と同じで、`issued-at` を含むデコード後の案内全体が同じ場合は「重複案内」として受理済み扱いにし、対象や状態を変更しない。
- `revision` が現在値と同じで、`issued-at` または内容が一つでも異なる場合は「競合案内」として不正扱いにし、状態を変更しない。`revision` または `issued-at` を比較可能な形へ検証できない案内も同様に拒否する。
- `revision` が現在値より大きい場合は「新しい案内候補」とし、構文・正規化・行間整合性の検証に成功したときだけ、その案内の対象、候補、順序、採用地点、確認、完了、モード、`revision` および `issued-at` を現在状態へ一括反映する。部分反映はしない。`revision` が現在値より大きいこと自体は新しい案内の条件であり、`issued-at` の前後関係や連続した世代番号を要求しない。

案内を取り込んだ別リーダーが再出力する場合は、`run` を元の値から変更せず、取り込んだ `revision` より 1 大きい値、再出力操作時点の `issued-at`、その時点の状態を出力する。したがって、別リーダーであることや端末時計のずれだけでは新しい周回にも競合にもならない。異なる `run` の案内を明示的な置換操作で取り込んだ場合だけ、現在の周回識別子も取り込んだ値へ置き換わる。[REQ-F-012][REQ-F-008]

案内の出力後に元のリーダーが進行・順序・対象を変更しても、取り込み済みの状態は自動更新されない。元のリーダーとの同期、差分反映、競合解決は行わず、別のリーダーが新しい案内を再度取り込む場合だけ、上記の取り込み操作が行われる。[REQ-F-010][REQ-F-012]

取り込んだ案内が手動順序を示していた場合は手動順序として、自動ルートを示していた場合は自動ルートのスナップショットとして表示する。新たな対象を追加または完了する場合は、取り込み後の利用者の現在モードに従って 7 章の規則を適用する。[REQ-F-008][REQ-F-012]

## 9. 保存と互換性

### 9.1 保存する情報

利用者が再読み込み後も周回を継続できるよう、プロダクトは現在の利用者周回情報をブラウザ内の永続的な保存領域へ保存できる。保存の技術方式は Design で決める。保存対象の意味は次の通りである。[REQ-F-008][REQ-F-009][REQ-F-014]

- 選択中の公開単位と、Treasure で必要なグレード。
- 利用者が登録した対象、名前、マップ、座標、Treasure の順次関係。
- Mob の候補集合、候補の確定/候補の意味、ルート採用地点、利用者確認地点。
- 完了/未完了、現在の自動ルートまたは手動順序、およびその表示上の区別。
- Mob の周回識別子 `run` と、最後に出力または取り込んだ案内の `revision` / `issued-at`。案内未出力の場合は世代情報を持たず、最初の出力を `revision: 0` とする。これらは同期情報ではなく、最後に扱ったスナップショットの出所と世代判定に使う外部意味を保持する。

### 9.2 保存しない情報と期間

マスターデータ、マスターデータの更新結果、ゲーム内の実際の討伐・開封・移動状態、ゲーム内チャットへの投稿結果、参加者の情報、アカウント認証情報は利用者の周回情報として保存しない。[REQ-F-013][REQ-F-014][REQ-S-001][REQ-S-004]

保存は現在の周回を再開するためのものであり、利用者が明示的に削除・リセット・置換するまで保持する。すべての対象が完了した後も、現在の周回の完了結果はそのまま表示できるが、長期履歴や統計として別の周回へ自動蓄積しない。[REQ-F-009][REQ-F-014]

保存全体を正常な現在周回として採用できるのは、公開単位と保存形式が対応し、必須の周回情報・対象識別情報・正規化済み位置情報・順序・完了/確認/採用地点の値、および案内情報を保存している場合の `run` / `revision` / `issued-at` がすべて検証でき、各対象が重複せず、順序が現在の対象集合と一対一に対応し、状態間の整合性が成立する場合だけである。いずれか一つの検証に失敗した場合は、保存全体を破損として扱い、部分復元へ進まない。[REQ-D-007][REQ-F-014]

ブラウザ再読み込み後は保存された現在周回を復元する。構造と整合性が有効な保存全体で、参照先のマスターデータだけが欠落・更新・不正になっている場合は、周回情報全体を保持したまま該当地点を未確認/計算対象外として表示し、ルートと進行の誤更新を防ぐ。マスターデータの問題を理由に、保存された座標、候補、順序、完了、確認または採用地点を別の値へ推測置換しない。[REQ-D-007][REQ-F-014]

保存された `run`、最後に扱った案内の `revision` および `issued-at` は、再読み込み後も同じ値として扱う。再読み込みは世代を初期化せず、次の同じ `run` の案内出力では保存された `revision` に 1 を加える。`issued-at` の保存値は出力時刻の情報として表示・保持できるが、再読み込み後の新旧判定や次の世代の決定には使用しない。[REQ-F-012][REQ-F-014]

Treasure Compass の保存情報を Mob Compass の対象へ、Mob Compass の保存情報を Treasure Compass の対象へ自動変換・共有しない。両者の保存データは公開単位ごとに非互換として扱う。[REQ-F-001][REQ-F-014]

破損、未知の公開単位、未知の形式、必須情報が欠けた旧形式、重複・矛盾する対象、順序と対象集合が一致しない状態、または完了・確認・採用地点の関係が検証できない保存情報は、保存全体を正常な現在周回として採用しない。一つの対象または一つの項目だけが不正であっても、保存全体の部分復元は行わない。初期化時にこの判定となった場合は、保存情報から一切の対象、順序、完了、確認、採用地点を復元せず、該当公開単位の空の現在状態を開始し、利用者が「保存データを復元できなかった」ことと、再登録または保存情報の消去が必要であることを識別できるようにする。破損した保存情報は正常状態として書き戻したり自動変換したりせず、既存の正しい周回を読み込み済みの場合はそれを破棄・上書きしない。破損情報から対象、ルート、完了、確認、採用地点を推測してはならない。[REQ-D-007][REQ-F-014]

保存領域のキー、シリアライズ形式、マイグレーション方式、削除方式の実装は Design / Implementation へ引き継ぐ。[REQ-F-014]

## 10. マスターデータ

### 10.1 必須情報と利用者から見える結果

マスターデータ管理者は、少なくとも次の情報を、Treasure / Mob の周回で参照できる状態へ整備する。地点の X/Y は 3.1 の座標契約で正規化でき、正規化後の値と有効範囲を利用者が識別できなければならない。[REQ-F-013][REQ-D-001]

- 地図の識別情報、表示名、対象グレードとの対応。
- 地図上の位置情報（正規マップ識別子、X/Y の有効範囲と、必要な高さ等）。
- 地図へ移動するための有効な移動拠点と、ルート補助評価に必要な料金・ロード時間情報。値の単位と、どのマップ間遷移へ適用するかも識別できるようにする。
- Mob の安定した識別情報と名前。
- Mob に対応する確定地点および候補地点、その地点が属する地図。
- 参考資料の出典、画像等の利用条件、確認状況。

マップ識別子とモブ識別子は、表示名の変更や別名の追加があっても同一対象を識別できる、ASCII の unreserved 文字（`A-Z a-z 0-9 - . _ ~`）だけからなる安定した外部識別情報とする。候補地点の外部識別は正規マップ識別子と正規化座標の組み合わせであり、同一モブ内で同じ組み合わせを重複公開しない。地図の表示名や画像は識別子の代替ではない。[REQ-F-004][REQ-F-013][REQ-F-014]

利用者は、マスター由来の地図・地点・モブと、自身の周回で登録・確認・完了した情報を識別できる。マスターの候補地点を利用者の確認地点として表示せず、利用者の確認をマスターの確定情報へ書き戻さない。[REQ-F-004][REQ-F-014]

### 10.2 欠落、不正、未知、更新

必須情報が欠落、型・範囲・参照先が不正、公開前の確認状態である、または利用者が選択した対象と対応しない場合、そのマスター情報は有効なルート地点として扱わない。該当する地図、拠点、モブ、候補地点を利用者が識別できる未確認/計算対象外として示し、誤ったルートや完了更新を成立させない。[REQ-D-007][REQ-S-005]

マスターデータを更新しても、既存の利用者入力、完了、確認、順序を自動削除・自動完了・別地点への推測置換をしない。更新後の参照で既存情報が有効でなくなった場合は未確認として表示し、利用者が再選択・再登録するまでルートへ含めない。自動ルート中に有効な地図、地点または移動負荷のマスター値が更新された場合は、更新後の値で自動ルートを再評価し、手動順序中は順序を保持したまま表示可能な遷移情報だけを更新する。[REQ-F-013][REQ-F-014][REQ-D-007]

マスターデータの更新で新しい候補地点が追加されても、既存 Mob の利用者周回にその候補を自動追加しない。新しい候補を現在の候補集合へ含めるには、利用者がその候補を明示的に登録または選択する。既存地点の識別子が維持されたまま表示名、画像、補助値だけが更新された場合は、同じ地点を再登録したり完了を解除したりせず、更新後の値で次回のルート評価を行う。[REQ-F-004][REQ-F-008][REQ-F-013][REQ-F-014]

管理者は、公開前に地図、移動拠点、モブ、位置情報、候補地点の整合性と出典・画像利用条件を確認し、誤りを把握した場合は訂正した版を公開する。プロダクトはゲーム状態の自動確認によってマスターデータの正確性を保証しない。[REQ-S-005][REQ-S-006]

マスターデータのファイル形式、JSON schema、ディレクトリ配置、バージョン管理、読み込み実装、管理画面、公開手順の具体方式は Design / Implementation へ引き継ぐ。[REQ-F-013][REQ-S-005][REQ-S-006]

## 11. エラー、安全性、禁止される暗黙動作

### 11.1 外部入力の扱い

空、不正、不完全、未知、解析不能な直接入力は、有効な対象・地点・完了として受理しない。8.2 の構文を満たすチャット案内または 9.2 の構造を満たす保存情報に含まれるが、現在のマスターデータだけで未知となる参照は、各節の規則に従って未確認として保持できる。入力を画面に表示する場合も、利用者が入力した文字列を HTML として解釈せず、文字列として表示する。入力を別の対象・マップ・座標へ推測変換しない。[REQ-D-007][REQ-S-001]

拒否された入力、未確認の入力、計算対象外のマスター、計算不能な対象は、成功した登録・候補採用・地点確認・完了と外部から区別できる。異常情報がある場合に、正常対象だけのルートを「全対象の最短ルート」と表示してはならず、対象集合に未確認項目があることを示す。[REQ-F-007][REQ-D-007]

### 11.2 明示操作と失敗原子性

登録、削除、ルート採用、地点確認、完了、手動順序変更、チャット取り込みは、対応する利用者操作が成功した場合だけ外部状態を更新する。解析・検証に失敗した入力や案内は、既存の対象、順序、確認、完了、保存を部分的に書き換えない。[REQ-S-002][REQ-D-007][REQ-F-008][REQ-F-009][REQ-F-012]

プロダクトは、次を自動で成立させない。

- ゲーム内での実際の討伐、宝箱開封、地点到着、移動。
- ルート表示による地点確認、候補の存在確認、モブ完了。
- チャット案内の出力によるゲーム内投稿。
- 別リーダーの取り込みによる元リーダーとの同期。
- マスター更新による利用者周回の自動移行。

## 13. 未決定事項と下流への引継ぎ

### 13.1 Design で決める事項

次の事項は、外部契約を変更しない範囲で Design が具体化する。

- UI の画面構成、コンポーネント責務、入力欄・選択欄・通知の配置。
- 座標を地図画像へ描画する変換、座標入力を画面部品へ接続する方法。ただし、ゲーム内マップ座標の意味、受理形式、正規化、表示丸めの契約は変更しない。
- 入力解析のコード構造、検証の分割、エラー処理の内部責務。ただし、3 章の同じ受理/拒否境界と正規化結果を返す。
- 経路探索アルゴリズム、探索方法、グラフ表現、計算量最適化、内部スコア、キャッシュ、候補組み合わせの内部表現。ただし、6 章の候補集合、比較規則、同順位、計算不能時の外部結果を変更しない。
- 状態所有、イベント、内部データ構造、コードレベル API、保存技術、保存形式の内部表現、保存の復元・削除実装。ただし、9 章の全体採用/全体拒否、マスター更新時の未確認化、期間、互換性の結果を変更しない。
- チャット案内の生成・コピー・取り込みを担うモジュール構成。ただし、8 章の行形式、percent-encoding、`run`、`revision`、version、`issued-at`、stale/duplicate/conflict/newer の外部 semantics を変更しない。
- マスターデータのファイル形式、内部 schema、配置、ロード、版管理、管理者向け更新・公開手順。ただし、10 章の利用者から識別できる必須情報、安定識別、出典・利用条件、訂正結果を満たす。

### 13.2 Implementation / Test で決める事項

コード、具体的なライブラリ・フレームワーク、ファイル構成、テストコード、fixture、ブラウザ確認、性能測定、CI、公開手順は本仕様で決めない。Implementation は、3〜11 章の外部契約を保ったまま具体化する。Test は、12 章の適合条件に対して、空・部分・不正・全角/半角・座標境界・未知マップ・重複・大量入力・複数候補・JSON ロード失敗・保存破損・グレード変更・リセット・再計算・案内の古さを検証できる具体的な方法を定める。[REQ-D-007][REQ-F-008][REQ-F-009][REQ-F-012][REQ-F-014]

### 13.3 Specification で採用しない事項

Requirements の単独根拠がない、または上流で対象外とされた参加者画面、リアルタイム同期、アカウント、サーバー共有、権限移譲、統計、通知、ゲーム連携、自動投稿、AI 判定、不要な共通モデルは、本仕様へ追加しない。[REQ-F-001][REQ-F-010][REQ-S-001][REQ-S-003][REQ-S-004]
