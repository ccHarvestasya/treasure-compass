## 1. 要件定義の目的・適用範囲

本書は、Treasure Compass と Mob Compass の v1 について、利用者およびマスターデータ管理者から見て満たされなければならない能力、制約、責任および結果を定義する。

Treasure Compass は現在運用中のトレジャーハント支援を継続し、既存の登録・地図・ルート・進捗の外部体験を大きく変えずに、手動順序、進捗の訂正および復元を改善する。Mob Compass は別のブラウザアプリとして新たに提供し、「ソロ」と「パーティ」で異なる登録・巡回を支援する。

本書では、正確な画面配置、入力構文、状態遷移、データスキーマ、保存方式、計算式、アルゴリズム、内部構造および具体的なテスト手順は決定しない。これらは Specification、Design、Implementation / Test で定める。

## 2. 上流コンセプトから継承する前提・境界

### 2.1 継承する判断

- Treasure Compass と Mob Compass は、別 URL、別の周回状態および別の保存境界を持つ独立したブラウザアプリである。
- 両アプリは、地図表示、地点選択、経路表示および進行管理の基本的な利用感を共有するが、対象モデル、登録フローおよび周回状態を統合しない。
- Mob Compass の「ソロ」はデイリー・ウィークリー手配書の一般モブから B モブまでを対象とし、「パーティ」は共有された A モブ以上だけを対象とする。
- 登録された巡回地点について、別マップへの移動と同一マップ内の探索を考慮し、移動・探索負担が最小となる巡回経路を算出する。
- 利用者が手動で変更した巡回順を自動計算より優先し、自動順序へ戻す場合は利用者の明示操作を必要とする。
- 実際のゲーム状態、モブの存在、討伐および現在地は自動取得・自動判定しない。
- マスターデータと利用者の周回情報を混在させない。

### 2.2 v1 対象外

- 不定形なゲーム内チャットの解析、Mob Compass 専用チャットマクロの要求、チャットからの一括登録
- 参加者向け閲覧画面、共有状態の同期、共同編集、リーダー間の自動引継ぎ
- サーバー、認証、高度な権限管理、常設コミュニティまたは FC の管理
- ゲーム内状態との自動連携
- 長期的な周回履歴、統計分析および通知
- デイリー一般モブの必要討伐数または途中討伐数の管理
- 初期リリースでの英語等の翻訳、多言語 UI、および Mob の正式名・別名・検索語の多言語対応。ただし、将来のローカライズを妨げないデータの整理は現行要件とする。

## 3. 利用者・外部主体・利用場面

### 3.1 利用者と外部主体

- **Treasure Compass 利用者**: パーティーメンバーの宝箱地点を登録し、巡回順と進捗を管理する。
- **Mob Compass ソロ利用者**: 手配書の一般モブおよび B モブを登録し、個人で討伐・探索する。
- **Mob Compass パーティリーダー**: 他者から得た A モブ以上の報告地点を手動登録し、パーティの巡回を管理する。
- **パーティ参加者**: リーダーからゲーム内チャット等で案内を受ける関係者であり、v1 の直接利用者ではない。
- **マスターデータ管理者**: 地図、移動拠点、対象、ランク、名称および候補地点を整備する。

### 3.2 代表利用場面

1. Treasure Compass 利用者がメンバーと宝箱地点を登録し、自動または手動の巡回順に沿って進行を管理する。
2. ソロ利用者が手配書の対象を名前や条件で探して登録し、一般モブと B モブを一つの巡回として進める。
3. パーティリーダーが共有された A モブ以上の地点を候補地点から選んで登録し、登録地点の最短巡回と進捗を管理する。
4. 利用者が中断後に同じブラウザでアプリを開き、保存された周回状態から再開する。

## 4. 機能要件

### 4.1 アプリと状態の分離

#### REQ-F-001 独立した公開単位

Treasure Compass と Mob Compass は、利用者が異なる URL で識別して直接利用できる別アプリとして提供されること。

#### REQ-F-002 アプリ間の状態分離

Treasure Compass の登録、順序、進捗、保存および消去は Mob Compass へ影響せず、Mob Compass の操作も Treasure Compass へ影響しないこと。

#### REQ-F-003 Mob モードの分離

Mob Compass は「ソロ」と「パーティ」を利用者が切り替えられ、現在のモードを識別できること。両モードの登録対象、順序、進捗および消去範囲は独立し、切り替えてももう一方の状態を失わないこと。

#### REQ-F-004 Mob モードの再開

Mob Compass を再び開いた利用者は、前回使用していたモードと、そのモードの保存済み周回状態から利用を再開できること。

#### REQ-F-005 共通する操作結果

Treasure Compass と Mob Compass は、対象固有の登録入口を維持しながら、地図上のマスター地点の選択、巡回順の手動変更、完了と取消、確認後の全消去、現在地点と完了状態の識別について、同じ意味の操作を一貫した利用結果として提供すること。正確な UI 部品、配置、文言および操作方法は Specification で定義する。

### 4.2 地図上のエーテライト表示

#### REQ-F-006 動的なエーテライト案内

地図画像は背景として扱い、対象マップに登録されたエーテライトのうち、検証済み T レコードに該当するものだけを、検証済みの共通地図情報からアプリの案内表示として描画すること。利用者は、対象マップのすべての有効なエーテライトを、通常の地図表示および地点選択表示の両方で継続的な案内表示の対象として確認できること。現時点で対応する G8、G10、G12、G14、G17 の全マップ画像では、画像に埋め込まれた町名・エーテライト表示を除去し、アプリの案内表示と重複させないこと。

#### REQ-F-007 アイコンと町名ラベルの表示

エーテライトアイコンは、そのエーテライトの実際のマップ座標に対応して表示すること。町名ラベルは他のラベルとの重なりを避けるためにアイコンの近くへ移動でき、アイコンとの対応を示すための接続線を必須としないこと。画面が狭い、または表示が過密な場合は、エーテライトアイコンを優先して表示し、町名ラベルの一部を省略または非表示にできること。ラベルの正確な配置・回避規則および表示上限は Specification で定義する。

#### REQ-F-008 エーテライト案内の非操作性

エーテライトアイコンおよび町名ラベルは案内表示専用とし、クリックまたはタップによって地点の登録、選択、変更、完了その他の周回状態の変更を発生させないこと。利用者がアプリ上で町名、座標その他のマスター情報を登録または編集する機能を提供しないこと。

### 4.3 Treasure Compass

#### REQ-T-001 既存の対象登録

Treasure Compass 利用者は、メンバーごとの現在の宝箱地点を手動で登録でき、既存のパーティチャット入力による一括登録も継続して利用できること。同じ時点では一人のメンバーに一つの宝箱地点が対応し、新しい地点を登録した場合はそのメンバーの現在地点として扱えること。

#### REQ-T-002 地図と巡回進捗

利用者は、登録した宝箱地点、巡回順、現在の巡回地点、完了済み対象および未完了対象を地図と進捗情報から識別できること。

#### REQ-T-003 手動順序の維持

利用者が巡回順を手動変更した後は、メンバーの追加、地点変更または削除によって既存対象の相対順序が変わらないこと。追加対象は末尾に置かれ、地点変更は同じ並び位置を維持し、削除は該当対象だけを外すこと。

### 4.4 Mob Compass の登録

#### REQ-M-001 モード別の登録対象

ソロでは一般モブから B モブまでだけを登録でき、パーティでは A モブ以上だけを登録できること。現在モードの対象外となるモブは登録候補にならないこと。

#### REQ-M-002 モブの検索と絞り込み

利用者は、正式名または登録済み別名の一部を入力してモブ候補を絞り込めること。また、拡張エリアおよび種別・ランクによって候補を絞り込めること。入力文字列だけから対象を推測登録せず、利用者が候補を選択した時点で対象を確定すること。

#### REQ-M-003 ソロ対象の候補地点登録

ソロ利用者が一般モブまたは B モブを選択した場合、そのモブについてマスターデータに登録された全候補地点を候補集合として一括登録すること。利用者へ X/Y/Z 座標の自由入力や、マスターにない任意地点の登録を要求しないこと。

#### REQ-M-004 一般モブの訪問地点

一般モブに複数の候補地点がある場合、全候補地点を最初から探索対象とはせず、同じマップの巡回全体の負担が最小となる一地点を現在の訪問先として採用すること。

#### REQ-M-005 B モブの探索対象

B モブは、登録された全候補地点を未探索の訪問先として扱い、いずれかで発見・完了するか、すべての候補地点を探索し終えるまで候補集合を維持すること。

#### REQ-M-006 パーティ対象の地点登録

パーティリーダーは、A モブ以上を選択した後、そのモブの出現マップにあるマスター登録済み候補地点から、報告された一地点を選択して登録できること。候補地点の選択を登録として即時に反映し、自由座標や任意地点は登録できないこと。

#### REQ-M-007 パーティ対象の地点変更

登録済みの A モブ以上を再選択して別の候補地点を指定した場合、同じモブの複数地点として追加せず、以前の報告地点を新しい地点で置き換えること。手動順序では並び位置を維持すること。

#### REQ-M-008 連続登録

Mob Compass は、対象を一件登録した後も利用者が登録操作を継続でき、巡回経路の確認へ自動的に切り替えないこと。

### 4.5 経路と順序

#### REQ-R-001 マップ間経路の最小化

自動経路は、現在の巡回対象について異なるマップへの遷移回数を第一に最小化すること。遷移回数が同じ候補では、テレポに伴うゲーム内通貨とロード時間を、いずれか一方を常に優先しない補助的な移動負荷として考慮すること。

#### REQ-R-002 同一マップ内経路の最小化

同じマップ内の自動経路は、ゲーム内 X/Y 座標の二次元直線距離に基づき、対象となる訪問地点を巡る総距離を最小化すること。Z 座標は地点識別、表示および経路評価に使用しないこと。

#### REQ-R-003 初回のマップ内開始地点

まだ現在地点を持たないマップの自動経路は、利用可能なエーテライトを開始地点とすること。複数のエーテライトがある場合は、そのマップの対象地点を巡る総距離が最小となるものを選ぶこと。

#### REQ-R-004 モード別のマップ内統合

ソロでは、同じマップにある一般モブの採用地点と B モブの未探索候補地点を一つの経路として算出すること。パーティでは、同じマップに登録された A モブ以上の報告地点を一つの経路として算出すること。

#### REQ-R-005 現在地点からの再計算

自動順序の利用中に地点を完了・探索した場合、同じマップの残りの経路は、その地点を現在地点として再計算すること。同じマップの対象追加または A モブ以上の地点変更でも、保存中の現在地点から再計算すること。

#### REQ-R-006 自動順序と手動順序

利用者は、自動計算された順序を手動で変更でき、現在が自動順序か手動順序かを識別できること。自動順序では対象状態の変化に応じて残りの順序を再計算できること。手動順序では、利用者が明示的に経路自動計算を実行して計算が成功するまで、既存の順序を自動で入れ替えないこと。

#### REQ-R-007 手動順序への追加

手動順序へ新しい一般モブまたは A モブ以上を追加した場合は、既存順序を変えず末尾へ追加すること。新しい B モブの候補地点は訪問地点単位で扱い、既存順序の末尾地点から近い順で末尾へ追加すること。既存順序が空の場合は、そのマップのエーテライトから近い順に置くこと。

#### REQ-R-008 手動順序での進行

手動順序で対象を完了した場合は、該当対象を現在の巡回対象から外し、残りの相対順序を維持すること。B モブの候補地点は、モブ全体を一つのまとまりとせず、一般モブの訪問地点と同じ単位で個別に並べ替えられること。

### 4.6 進行、完了および訂正

#### REQ-P-001 対象の完了

利用者は Treasure の宝箱対象、Mob の一般モブ、B モブまたは A モブ以上を対象単位で完了にできること。完了済み対象は元の進捗位置に完了表示で残し、未完了の巡回経路から除外すること。一般モブの討伐数は記録せず、利用者の完了操作だけを扱うこと。

#### REQ-P-002 完了の取消

利用者は完了済みの各対象を個別に未完了へ戻せること。手動順序では元の位置へ戻し、自動順序では保存中の現在地点から残りの経路を再計算すること。B モブでは、完了直前の候補地点ごとの探索状態も復元すること。取消対象以外の後続操作や一般的な操作履歴は巻き戻さないこと。

#### REQ-P-003 B モブの次の地点

B モブが現在の候補地点にいなかった場合、利用者はその地点を探索済みにして残りの探索経路から外し、現在地点から次の候補地点へ進めること。この能力は一般モブには提供しないこと。

#### REQ-P-004 次の地点の取消

利用者は、直前に実行した B モブの「次の地点へ」に限り取り消せること。取消により、その操作で探索済みにした地点、順序および現在地点を操作直前の状態へ戻すこと。過去の任意の探索操作は選択して取り消せないこと。

#### REQ-P-005 B モブの未発見と再探索

B モブの全候補地点を探索しても発見できなかった場合は完了にせず、未発見であることを表示すること。利用者が探索のやり直しを明示した場合は、全候補地点を未探索へ戻し、その時点の現在地点から探索経路を再計算すること。時間経過だけでは自動的に再探索状態へ戻さないこと。

### 4.7 保存と消去

#### REQ-L-001 周回状態の保存と復元

Treasure Compass、Mob Compass のソロおよびパーティについて、自動・手動の区分、巡回順、登録対象、選択地点、完了状態、B モブの候補地点別探索状態および最後に完了・探索した現在地点を、それぞれ独立して保存し、同じブラウザで再読み込みまたは再訪した際に復元できること。

#### REQ-L-002 現在地点からの再開

復元後は保存された現在地点から残りの巡回を継続できること。一日限りの周回を前提とし、時間経過による自動消去や、エーテライト起点へ強制的に戻す処理を行わないこと。

#### REQ-L-003 Treasure の消去範囲

Treasure Compass の全消去は Treasure の登録内容と進捗だけを対象とし、Mob Compass の状態を変更しないこと。

#### REQ-L-004 Mob の消去範囲

Mob Compass の全消去は現在選択中のソロまたはパーティだけを対象とし、もう一方のモードおよび Treasure Compass の状態を変更しないこと。

#### REQ-L-005 消去の確認

全消去を実行する前に、消去対象となるアプリまたはモードを利用者が識別して確認でき、確認した場合だけ消去すること。

#### REQ-L-006 保存失敗時の保証

周回状態を保存できなかった場合は、利用者が保存失敗を識別できること。保存されていない変更を保存済みとして扱わず、最後に正常保存された状態を破壊しないこと。

### 4.8 マスターデータ

#### REQ-A-001 巡回基礎情報

管理者は、巡回に必要な地図、エーテライト、対象の正式名、登録済み別名、拡張エリア、種別・ランク、出現マップおよび X/Y 候補地点を整備できること。

#### REQ-A-002 マスターと周回情報の分離

アプリは、管理者が整備するマスターデータと、利用者が登録・選択・完了・探索した周回情報を異なる情報として扱い、候補地点であることだけから発見・確認・完了済みとみなさないこと。

#### REQ-A-003 共通地図情報

マスターデータ管理者は、対応マップごとに、検証済み T レコードに該当するエーテライトの実座標、町名および表示に必要な情報を、グレードに依存しない共通の地図情報として整備できること。legacy R レコードは共通の地図情報へ採用しないこと。同じマップが複数グレードに登場する場合も、町名・エーテライト情報をグレードごとに重複管理せず、共通情報として各グレードから参照できること。

#### REQ-A-004 有効なエーテライトの境界

アプリが共通地図情報へ採用し、エーテライトとして表示・参照および経路計算に使用できるのは、対象マップとの参照が解決できる検証済み T レコードだけとすること。legacy R レコードは、検証済みまたは対象マップとの参照が解決できる場合でも、共通地図情報、表示、参照および経路計算に使用しないこと。その他の未検証、参照不能または対象範囲外の情報も、推測採用しないこと。

## 5. データ・入力・出力に関する要件

#### REQ-D-001 利用者入力の確定

対象名の検索結果、候補地点の選択、手動順序、完了、探索結果および取消は、利用者が選択または明示操作した結果だけを周回状態へ反映すること。

#### REQ-D-002 無効または未知の情報

空、不正、不完全、未知またはマスター参照を解決できない入力・保存データを、正常な対象、地点または進捗として推測採用しないこと。処理できない情報を利用者が識別でき、誤った成功、ルート算出または進捗更新を起こさないこと。

#### REQ-D-003 経路結果の識別

利用者は、現在のアプリとモード、巡回対象、対象が属するマップ、訪問地点、巡回順、現在地点、完了・未完了、および B モブの未探索・探索済み・未発見を識別できること。

#### REQ-D-004 初期ローカライズ境界

初期リリースでは、マップ名、町名、対象名および UI を日本語で提供すること。将来別の言語を追加する際に、名称を言語別に扱うことを妨げないデータの整理とすること。ただし、初期リリースに英語等の翻訳、多言語 UI、または Mob の正式名・別名・検索語の多言語照合を含めないこと。Treasure の既存の日本語によるマップ名・町名の利用およびチャット一括登録は、既存の Treasure 要件の範囲で扱うこと。

## 6. 非機能・品質要件

#### REQ-Q-001 スマートフォン対応

Treasure Compass と Mob Compass はスマートフォンで利用でき、縦向きで各アプリに該当する対象登録、地点選択、経路確認、完了・取消および全消去を行えること。Mob Compass ではソロ／パーティのモード切替も行えること。横向きでも各アプリに該当する主要操作が利用不能にならないこと。

#### REQ-Q-002 既存 Treasure との継続性

Treasure Compass の既存利用者が、現在のグレード、メンバー登録、チャット一括入力、地図表示、経路表示および完了管理を継続して利用できること。既存の保存データを根拠なく破棄しないこと。

本コンセプトから、応答時間、可用性、同時利用者数その他の数値品質目標は導出できないため、根拠のない閾値は本書で追加しない。

## 7. 安全性・責任・外部連携上の制約

#### REQ-S-001 ゲーム状態との境界

アプリは、モブの出現、討伐、現在地その他のゲーム状態を自動取得・自動判定したものとして扱わず、利用者が入力・選択・完了した情報をもとに支援すること。

#### REQ-S-002 利用者の責任

対象の選択、報告地点の選択、順序の採用、完了、探索結果および参加者への伝達は利用者が行うこと。アプリは利用者の明示操作なしに発見・討伐・完了したものとして扱わないこと。

#### REQ-S-003 チャットとの境界

Mob Compass は、ゲーム内チャットの内容を解析・一括登録せず、専用マクロの利用を要求しないこと。パーティリーダーは受け取った報告を確認し、対象と候補地点を手動登録できること。

#### REQ-S-004 共有機能との境界

パーティの巡回状態はリーダーが管理し、参加者向け閲覧画面、同期、共同編集またはリーダー交代を v1 の必須能力としないこと。

#### REQ-S-005 マスターデータの責任

マスターデータ管理者は、地図、移動拠点、モブ、ランク、名称、候補地点、動的なエーテライト表示に用いる画像資産、出典および画像利用条件の正確性、更新、確認および公開に責任を持つこと。アプリはゲーム状態の自動確認によってその正確性を保証しないこと。

## 9. 未決定事項 / Specification への引継ぎ

### 9.1 Requirements で決定済みの外部判断

1. Treasure と Mob は別 URL・別周回状態・別保存境界であり、Mob のソロとパーティも独立状態とする。
2. ソロは一般モブから B モブまで、パーティは A モブ以上だけを登録対象とする。
3. 一般モブは候補集合から巡回全体の負担が最小となる一地点を採用し、B モブは全未探索候補地点を探索対象とし、A モブ以上は報告された一地点を登録する。
4. 自動経路はマップ間遷移回数を第一に最小化し、同一マップでは X/Y 二次元距離による総距離を最小化する。初回は最適なエーテライト、進行中は保存された現在地点を開始地点とする。
5. 手動順序は利用者が明示的に自動計算を成功させるまで維持し、対象変更・完了によって既存の相対順序を自動で入れ替えない。
6. 完了は対象ごとに取り消せ、B モブの「次の地点へ」は直前の一回だけ取り消せる。全候補探索後は未発見とし、明示操作で再探索できる。
7. 周回状態はアプリ・モードごとに保存・復元し、全消去は確認された現在の対象範囲だけへ作用する。
8. Mob のチャット解析、専用マクロ、一括登録および共有同期は v1 の対象外とする。
9. 対象固有の登録入口は分けたまま、同じ意味を持つ地点選択、手動順序、完了・取消、確認付き全消去および状態識別は、両アプリで一貫した利用結果とする。
10. 保存失敗は利用者が識別でき、未保存変更を保存済みとして扱わず、最後に正常保存された状態を保持する。
11. 検証済み T レコードだけを有効なエーテライトとして共通地図情報へ採用し、通常の地図表示と地点選択表示の両方への案内表示、参照および経路計算に使用する。legacy R レコードは共通地図情報、表示、参照および経路計算に使用しない。アイコンは実座標へ置き、町名ラベルは近接範囲で重なりを避け、狭いまたは過密な表示ではアイコンを優先して一部を省略・非表示とする。案内表示は操作対象にしない。
12. 対応中の全マップ画像から埋め込みの町名・エーテライト表示を除去し、アプリ表示と重複させない。同じマップのエーテライト情報はグレード間で共通化し、初期リリースは日本語のみとする。将来のローカライズを妨げないデータ整理は行うが、英語等の翻訳、多言語 UI、Mob 名称・別名・検索語の多言語対応は v1 に含めない。

### 9.2 Specification へ引き継ぐ事項

- 二つの URL の識別方法と、利用者が各アプリを直接開く際の正確な外部動作。
- Mob のモード切替、登録と巡回経路の表示切替、登録後に同じ入力状態へ留まる正確な画面動作。
- Treasure の既存チャット一括入力を含む入力形式、必須項目、上限、重複、未知情報および解析不能入力の扱い。
- モブ名・別名の部分一致、複数フィルタの組み合わせ、候補確定、重複登録の正確な規則。
- 一般モブ、B モブ、A モブ以上の候補地点、採用地点、探索済み、完了、未発見の正確な状態と表示および遷移。
- パーティで A モブ以上の候補地点を選択して即時登録する正確な操作。マップダイアログ案は暫定であり、要件を満たす UI 契約を Specification で再確認する。
- マップ間遷移、料金、ロード時間、同一マップ距離、複数エーテライト、同率候補および計算不能時の正確な評価・表示契約。
- 自動・手動の切替、追加・変更・削除・完了・取消・探索・再探索時の正確な状態遷移と、現在地点・順序の復元規則。
- 保存対象の正確な形式、保存失敗の表示と状態遷移、破損・旧形式・マスター参照不能時の外部動作および既存 Treasure 保存データとの互換性。保存失敗時は `REQ-L-006` の保証を維持する。
- 全消去の確認表示、取消可能範囲、成功・失敗時の正確な外部結果。
- スマートフォン縦向き・横向きでの表示領域、操作配置、対応画面幅および検証条件。
- エーテライト案内表示の正確な表示対象、地図表示・地点選択表示との関係、ラベルの自動回避、近接範囲、省略・非表示の判定、画像との重複除去および表示対象外情報の扱い。
- 共通地図情報の項目、値域、参照整合性、グレード間の統合、既存データにおける T レコードの採用と legacy R レコードの除外、更新・確認・訂正・公開および出典・画像利用条件の管理契約。
- 既存のエーテライト視覚資産を再利用する場合の採否、出典・利用条件および具体的な資産の扱い。画像の編集手段や資産ライブラリの選択は Implementation で定める。
- 初期日本語データの名称表現と既存 Treasure のマップ名・町名照合および一括登録との正確な関係、将来の言語追加時に必要となる名称の外部契約。Mob 名称・別名・検索語の多言語対応は将来課題として扱う。

### 9.3 Design / Implementation / Test の事項

- 経路算出アルゴリズム、内部データモデル、状態所有、保存技術、コンポーネント構成、ビルド入口、公開先および共有コードの構成。
- 具体的な画面実装、入力解析、データ検証、マスターデータ配置、エラー処理および移行処理。
- 本 Requirements と後続 Specification を検証するテストデータ、操作手順、テストコードおよび実行環境。
