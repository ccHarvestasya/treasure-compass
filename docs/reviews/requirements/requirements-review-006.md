## 4. 総評

Requirements は、更新された Concept の主要な変更を外部から確認可能な要求へ展開できている。Treasure と Mob の別 URL・別状態・別保存境界、Mob のソロ／パーティ、モード別ランク、名前検索、候補地点登録、一般モブ・B モブ・A モブ以上の異なる扱い、マップ間・同一マップ内の最短経路、自動・手動順序、完了・取消、B モブの探索進行、復元・消去、スマートフォン対応が Requirement と Acceptance に追跡できる。

旧版の「全モブを一律に扱う」「チャット案内を取り込んでリーダー交代する」という要件は削除され、チャット解析・専用マクロ・一括登録を対象外とする最新判断へ置き換えられている。正確な UI、状態遷移、保存形式、計算式、アルゴリズムは後工程へ分離され、工程境界も概ね適切である。

一方、保存を中核能力としながら、保存失敗時に利用者へ何を保証するかが Requirement ではなく Specification への引継ぎだけに置かれている。また、Concept が中核価値としている両アプリの共通操作感は継承事項として記載されるだけで、Requirement と Acceptance に対応していない。スマートフォン要件には、Mob 固有のモード切替が Treasure にも適用されるように読める軽微な不整合がある。

## 5. 指摘事項

### RR-006 — Major — 保存失敗時に保証すべき外部結果が未定義

- **状態:** New
- **対象箇所:** `REQ-L-001`、`REQ-L-002`、`REQ-D-002`、9.2「保存対象の正確な形式、保存失敗・破損・旧形式…」
- **事実:** 周回状態を保存・復元できることは要求しているが、保存できなかった場合に、利用者が失敗を識別できること、未保存状態を保存済みとして扱わないこと、最後に正常保存された状態を破壊しないことが Requirement または Acceptance にない。保存失敗時の外部動作自体を Specification へ委ねている。
- **根拠:** Concept 7 は保存失敗を利用者へどう伝えるかを要件定義への問いとしている。保存・復元は Concept の成功状態と `REQ-L-001` の中核能力であり、成功と失敗の外部境界は Requirements の責務である。
- **影響:** 下流が、保存失敗を通知して最後の正常状態を保つ契約と、成功表示のまま再訪時に状態を失う契約のどちらも選べる。利用者は周回を再開できるという要件が成立したか判断できない。
- **最小修正:** 保存失敗を利用者が識別でき、未保存の変更を保存済みとして扱わず、最後に正常保存された状態を破壊しないことを外部 Requirement と Acceptance に追加する。正確な文言、保存方式、原子性の実現方法は下流へ残す。
- **再確認条件:** 保存成功時と失敗時の外部結果が Requirement で区別され、Acceptance から成立を判断できること。

### RR-007 — Major — 共通操作感が検証可能な Requirement へ展開されていない

- **状態:** New
- **対象箇所:** 2.1「両アプリは…基本的な利用感を共有する」、`REQ-T-001`–`REQ-T-003`、`REQ-M-006`–`REQ-M-008`、`REQ-P-001`–`REQ-P-002`、`REQ-L-003`–`REQ-L-005`、10.1 の1行目
- **事実:** Concept は地図表示、地点選択、経路表示、進行管理の基本的な利用感を共有することを中核価値としている。Requirements は個別能力を定義しているが、同じ意味の操作について両アプリで揃えるべき外部結果が Requirement と Acceptance にない。Traceability はこの Concept 判断を `REQ-F-001`–`REQ-F-004` と `REQ-Q-001` へ対応させているが、これらは公開・状態・モード・スマートフォンの要求であり、共通操作感を扱わない。
- **根拠:** Concept 1、2、3、5、6 は、対象固有の登録方法を保ちながら、意味が同じ地図・地点選択・経路表示・進行操作を同じ感覚で扱えることを明示している。ユーザーは、地点選択、手動並べ替え、完了・取消、確認付き消去、現在地点・完了状態の識別を揃える方針を確定している。
- **影響:** 個別要件を満たしながら、Treasure と Mob で同じ意味の操作が互いに異なる体験となる実装も許容され、上流の提供価値を Acceptance で判定できない。
- **最小修正:** 対象固有の入口は分けたまま、同じ意味を持つ地点選択、手動順序、完了・取消、確認付き消去、現在地点・完了状態の識別について、両アプリで一貫した利用結果を提供する Requirement と Acceptance を追加する。正確な部品、配置、文言、ジェスチャーは Specification へ残す。
- **再確認条件:** 共通化する操作と対象固有の操作の境界が Requirement と Acceptance から追跡でき、Concept の共通操作価値が形式的な継承文だけに留まらないこと。

### RR-008 — Minor — スマートフォン要件が Treasure に Mob 固有操作を要求するように読める

- **状態:** New
- **対象箇所:** `REQ-Q-001`、`AC-018`
- **事実:** `REQ-Q-001` は Treasure と Mob の双方を主語としたうえで、縦向きで「モード切替」を行えることを要求している。しかしモード切替は Mob のソロ／パーティ固有であり、Treasure には対応するモードがない。
- **根拠:** Concept と `REQ-F-003` はソロ／パーティを Mob 固有の区分としている。
- **影響:** Treasure に不要なモード機能を追加する要求、または `REQ-Q-001` を文字どおり満たせない要求として解釈され得る。
- **最小修正:** モード切替を Mob にだけ適用するか、「各アプリで該当する主要操作」として適用範囲を明示する。
- **再確認条件:** Treasure と Mob のスマートフォン受け入れ対象がそれぞれ一意に読めること。
